# v0.9.5-F6C Specification - SubmissionService Persistence Dependency Narrowing

**Date:** 2026-08-02
**Status:** ACTIVE
**Baseline:** `3f1a923` (v0.9.5-F6B verification); F2-F6B commits are
ancestors. Branch `master`, HEAD `3f1a923`.
**Authorization:** Owner-authorized F6C stage (pasted instruction file).
**Full-core baseline:** 589 passed, 8 skipped (equals the completed F6B
verification value at HEAD `3f1a923`).

## Objective

Behavior-preserving persistence dependency refactor: remove the broad,
inherited `SubmissionRepository` dependency from the active
`SubmissionService` constructor and runtime state and replace it with four
owner-aligned, consumer-owned structural Ports; remove the two CALF
persistence `hasattr` capability guards; preserve every collaborator, write
order, independent commit, and failure-after-partial-success behavior; supply
only existing facade-owned repository instances through every composition
path.

## 4. Exact four Port signatures

Defined in `app/services/submission.py` with `typing.Protocol` +
`@runtime_checkable` (structural satisfaction checks are used by tests),
mirroring the F5A/F5B/F6B port pattern. Signatures from current HEAD source:

```python
@runtime_checkable
class SubmissionSystemPort(Protocol):
    def record_versions(self, versions: dict[str, str]) -> None: ...


@runtime_checkable
class SubmissionDataPort(Protocol):
    def save_essay(self, submission: EssaySubmission, *, synthetic: bool = False) -> int: ...
    def prior_records(self, submission: EssaySubmission) -> list[dict[str, Any]]: ...
    def get_submission_bundle(self, essay_id: int) -> dict[str, Any] | None: ...
    def save_feedback(self, essay_id: int, result: ProviderResult, analysis_version: str) -> None: ...
    def save_history(self, student_id: str, essay_id: int, history: HistoryResult) -> None: ...


@runtime_checkable
class SubmissionAnalysisPort(Protocol):
    def save_analysis_run(self, essay_id: int, analysis: AnalysisResult) -> AnalysisResult: ...
    def save_analysis(self, essay_id: int, analysis: AnalysisResult) -> None: ...
    def save_diagnosis(self, essay_id: int, diagnosis: DiagnosisResult) -> None: ...


@runtime_checkable
class SubmissionCalibrationPort(Protocol):
    def save_diagnostic_calibration(
        self, essay_id: int, calibration: DiagnosticCalibrationResult,
    ) -> DiagnosticCalibrationResult: ...
    def get_diagnostic_calibration(self, essay_id: int) -> DiagnosticCalibrationResult | None: ...
```

Concrete satisfiers: `SQLiteSystemRepository`, `SQLiteSubmissionRepository`,
`SQLiteAnalysisRepository`, `SQLiteCalfRepository`. No port inherits from the
central Protocol hierarchy; no port contains a method owned by another port;
no concrete SQLite or `Database` import in the Service module.

## 6. Legacy SubmissionRepository decision

The legacy local inherited `SubmissionRepository` declaration remains in
`app/services/submission.py` (removing it would broaden the stage into
central/local Protocol cleanup). It is no longer the active constructor type,
no longer a field type, and no longer required by `build_submission_service`
or any active caller. Its later removal is recorded as Protocol-consolidation
debt.

## 7. Capability-guard removal decision

Both CALF methods (`save_diagnostic_calibration`, `get_diagnostic_calibration`)
are capability-guarded with `hasattr` at baseline. Every active production,
operational, and test path can supply the existing facade-owned
`SQLiteCalfRepository` (verified during Phase 0 inventory). The guards are
removed: `submit` calls `calibration_repository.save_diagnostic_calibration`
when `calibration is not None`; `regenerate_feedback` calls
`calibration_repository.get_diagnostic_calibration(essay_id)` unconditionally.
The branch conditions deciding whether calibration runs are preserved.

`record_versions` remains inside `SubmissionService.__init__` (one call per

## 10. Exact submit sequence (current HEAD, authoritative)

1. (if `revision_of_submission_id`) `revision_service.validate_relationship`
2. `submission_repository.save_essay` (WRITE)
3. `analyzer.analyze` + `append_product_fluency_metric`
4. `analysis_repository.save_analysis_run` (WRITE)
5. `analysis_repository.save_analysis` (WRITE)
6. `diagnoser.diagnose`
7. (if `calibrator`) `submission_repository.prior_records` per genre filter
8. (if `calibrator`) `calibrator.calibrate`
9. `analysis_repository.save_diagnosis` (WRITE)
10. (if `calibration is not None`)
    `calibration_repository.save_diagnostic_calibration` (WRITE; guard removed)
11. (if revision) `revision_service.create_relationship`
    (three independent commits)
12. `history.summarize` (LearnerHistoryService read)
13. (if learner service) `learner_profile_service.recalculate` +
    `progress.enrich_history` (learner writes)
14. feedback contexts, reliability assessment (conditional), `router.generate`
15. (if revision snapshot) `revision_service.group_summary` + `.trajectory`
16. `submission_repository.save_feedback` (WRITE, multi-table)
17. `submission_repository.save_history` (WRITE)

## 11. Exact regenerate-feedback sequence

1. `submission_repository.get_submission_bundle` (READ; missing -> `LookupError`,
   no diagnosis -> `ValueError`)
2. `learner_profile_service.latest_or_recalculate` (if configured)
3. `revision_service.latest` (if configured and bundle has revision group)
4. `calibration_repository.get_diagnostic_calibration` (guard removed)
5. feedback contexts + reliability assessment (conditional) + `router.generate`
6. `submission_repository.save_feedback` (WRITE)

Public signature unchanged; F6B Admin regeneration depends on it.

## 12. Repository and collaborator write boundaries

`save_feedback` remains one repository-owned multi-table operation (feedback
records, exercises, LLM call records; one connection, one commit). No
Repository-owned multi-table operation (`save_essay`, `save_analysis_run`,
`save_analysis`, `save_diagnosis`, `save_diagnostic_calibration`,
`save_history`) is split, relocated, or guarded differently. Learner
snapshot/evidence writes stay inside the Learner repository via
`LearnerProfileService`/`ProgressService`; Revision writes stay inside
`RevisionService`.

## 16. Database/provider isolation plan

Every write-capable run uses `PYTHON_DOTENV_DISABLED=1`, `DATABASE_URL`
absent, `DATABASE_PATH` inside a fresh unique temporary directory,
`LLM_PROVIDER=local`, resolved-path assertions, development-database
SHA-256/size/mtime checks before and after (never opened), cleanup, and
port-free checks, via the F6C isolation runner (F6B runner pattern; allow-list
= accumulated F2-F6C approved diff: F6B entries plus
`app/services/submission.py` and `app/services/factory.py`; no wildcards).
No live external provider calls; fake/local analyzers and providers only.

## 17. Rollback plan

If a focused check fails, identify the smallest affected Port/branch/
collaborator/composition seam, reproduce with one focused test, compare
against the Phase 0 source-derived sequences, repair only that component,
rerun focused checks, and only then run the full suite. If completion requires
any repository/SQL/transaction/learner/Revision/Admin/API change or a
capability-absent fallback, stop and create
`docs/development/BLOCKER_REPORT_V0.9.5_F6C.md`.

## 18. Stop conditions

Stop and create the blocker report if completion requires: changing a
Repository implementation, SQL, a transaction boundary, `RevisionService`,
learner Service behavior, `AdminReanalysisService` behavior, the `Database`
constructor or public surface, API paths/schemas, a broad compatibility
fallback, a proxy/Service Locator/Unit of Work/DI framework, a live external
provider call, opening or writing the development database, or beginning F6D
or a later stage. Also stop if a fifth direct Repository owner is found, an
active caller cannot receive the existing facade-owned instances, preserving
behavior requires a new cross-Repository transaction, or removing a CALF
capability guard would break an active production path.
