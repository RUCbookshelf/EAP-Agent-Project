## Frozen design

### Deterministic longitudinal contract

- Add versioned `LongitudinalAssessment` fields: status, scope, comparable independent task count, minimum required, revision-group count, draft count, comment, bounded History Evidence IDs and limitations.
- Status values are `unavailable`, `pairwise_only`, `provisional_pattern`, `descriptive_trend_available` and `not_comparable`; scope values are `cross_task` and `within_task_revision`.
- The application service derives facts from the persisted task-aware Snapshot and revision records. The LLM may supply readable wording but cannot alter counts, scope, status, thresholds or evidence IDs.
- A deterministic server comment replaces only an empty, contradictory or unsafe longitudinal comment. A wording-only failure must not discard otherwise valid feedback or invoke LocalDemo.
- Retain the legacy `longitudinal` field for old clients while returning `longitudinal_assessment` in v0.7.1 responses.

### Validation and provider state

- Validate the structured longitudinal state first. No fixed phrase is required. Reject trend, ability-growth or nonexistent-evidence claims when the state does not permit them.
- Correction instructions identify the failed field and required facts. Valid quotations, findings, priorities and practices remain unchanged.
- Classify provider execution as `external_success`, `external_success_with_server_repair`, `request_failed`, `response_parse_failed`, `response_validation_failed`, `correction_failed`, `fallback_success` or `fallback_failed`.
- Return and persist a safe provider-status summary containing provider/model, request and validation states, correction attempt/result, server repair, fallback use/reason code, sanitized reason and retry count. Existing provider fields remain available.
- Deduplicate repeated failures and never expose keys, raw model responses, request content, internal paths or stack traces.

### Positive finding reliability

- A positive finding remains an exact contiguous essay quotation plus a description of an observable textual feature.
- Configured ability-inference phrases are invalid. A finding-only violation is safely repaired without losing valid priorities, exercises or revision evidence.

### Within-task revision trajectory

- Build a lightweight API-owned trajectory for one Revision Group: ordered draft chain, pairwise snapshots, first-to-latest comparison, diagnosis/metric changes, previous-priority state, current-priority state, uptake candidates, major-rewrite flag, attribution confidence and explicit limitations.
- Multiple drafts never increase cross-task independent-task or representative counts. Revision change never becomes ability growth, quality improvement or causal feedback uptake.
- Existing append-only Revision Snapshots remain unchanged and readable.

### API, configuration and persistence

- Add backward-compatible response fields `feedback_provider_status`, `longitudinal_assessment`, `revision_group_summary`, `within_task_revision_trajectory` and `ui_empty_states`.
- Empty-state codes include `NO_SELECTED_PRIORITY`, `NO_TARGETED_PRACTICE`, `INSUFFICIENT_CROSS_TASK_HISTORY`, `MAJOR_REWRITE_LIMITS_ATTRIBUTION` and `NO_PREVIOUS_PRIORITY`; UI copy is localized outside core services.
- Create and activate `config-v0.7.1` as a child of preserved `config-v0.7.0`, adding only the requested non-sensitive validation, finding, UI and revision-UI options.
- Use an additive migration only when new persistence is necessary. Preserve migration-8 data, old feedback/Snapshot parsing and configuration rollback. No database is deleted or rewritten.

### Streamlit boundary

- Streamlit remains an HTTP API client and never calculates business facts.
- Submission results use `Feedback`, `Revision`, `Progress`, `Evidence` and `Research Audit` tabs with a student/research-audit mode switch and a concise status summary.
- Every major empty section explains why it is empty. Ratios and lexical metrics include definitions and limitations. Connectives are deduplicated and grouped by function; student view defaults to discourse-organizing expressions while research view retains complete counts.
- Rerendering, tab changes and audit expansion reuse the submitted API response; they do not call the LLM, analyzer or Snapshot builder again.
