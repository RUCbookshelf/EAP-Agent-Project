## 1. Stage objective

Harden and prove the complete end-to-end product journey:
Writing submission -> AnalysisRun -> evidence-supported feedback -> selected
feedback priority -> Practice Target -> Exercise Instance -> Exercise Attempt
-> Practice Evaluation -> revised submission -> conservative revision-response
observation -> Learning Journey event presentation -> Research Learning
Process trace.

This stage determines why tested Learning Journey pages were empty and repairs
the confirmed cause. It does not populate journeys with invented evidence and
never claims mastery, acquisition, learning gain, intervention effect, causal
improvement, transfer achieved, proficiency increase, CEFR movement, or
feedback effectiveness.

### 3.2 Confirmed root cause of empty Learning Journeys

The journey page (Student View Learning Journey) renders events only from
`feedback_engagement_traces` and `transfer_evidence_candidates`
(`app/ui/pages/student_pages.py`, `render_learning_journey_page`). Direct
inspection shows:

- `FeedbackEngagementTrace.create_engagement_trace()` exists in
  `app/practice/service.py` but has **zero callers** in application code.
- The repository persistence and list functions exist
  (`save_feedback_engagement_trace`, `list_feedback_engagement_traces`) but
  nothing ever writes a trace.
- `feedback_engagement_traces` is empty for every learner
  (current DB: 0 rows; pre-v0.9.3 audit: 0 rows for S02/S03/S09).
- `transfer_evidence_candidates` is likewise empty and has no callers.
- Practice records are also empty (0 targets/exercises/attempts/evaluations),
  and `PracticeEvaluation`/within-task/transfer flows have **no API or UI
  wiring** (service methods and repository methods exist but are never called
  from `app/api/main.py` or the UI).

Therefore the empty-journey cause is **cause 3 in the taxonomy: missing event
creation after valid actions** — the application never creates journey events,
plus **cause 9: unsupported assumptions about feedback engagement** in the old
page (it treated traces as if practice/engagement happened, and displayed a
"Submit an essay" empty message even when essays exist — DATA-001). Causes 1,
2, 4, 5, 6, 7, 8, 10 were examined: no evidence of retrieval, aggregation,
association, state, or rendering defects; the records simply never exist.

Additional confirmed gap: **S02's existing feedback records contain zero
selected priorities** (feedback_json priority_feedback is empty for essays
1-3 and 13). This is legitimate Diagnostic Gate behavior (e.g., essay 13's
repeated word "parks" matches its writing prompt, so the prompt-term penalty
kept the signal below threshold, gate_result=monitor). Any journey UI must
represent this accurately as "feedback available but no eligible priority"
rather than implying a defect.

### 3.3 Feedback engagement semantics decision

`FeedbackEngagementTrace` is an explicit, write-time record intended for
defined engagement actions. Current semantics are ambiguous and no caller
exists. Conservative decision (documented here and in the Decision Log):

- Journey events are **derived at read time from authoritative source
  records** (essays, analysis runs, feedback records, practice targets,
  exercise attempts, practice evaluations, within-task response candidates,
  transfer evidence candidates). Every rendered event maps to a real source
  record; no event is created by page rendering, locale switching,
  navigation, or refresh.
- `FeedbackEngagementTrace` remains the model for explicit engagement actions
  and is **not written by this stage**; the journey does not depend on it.
- Page display is never engagement. Practice availability is never evidence
  of completed practice. Revision is never evidence of learning.

### 3.4 Deterministic demo fixture selection

The deterministic demo uses synthetic learner `DEMO-001` and a repetition
fixture whose flagged signal is not a prompt artifact:

- Prompt: "What actions matter for sustainability?"
- Essay: a clearly synthetic repetition text (repeated sentence-initial
  "People should ...") that legitimately produces a Diagnostic-Gate-selected
  `lexical_repetition` priority with the current local deterministic pipeline
  (verified by submission-service probe: empty states = [], selected priority
  present). This does not weaken the gate.

## 4. Implemented design (v0.9.3-C)

### 4.1 Journey event contract

`JourneyEvent` fields: event_type (stable), title/description localization
keys + parameters, source_record_type, source_record_id, learner_id, task_id,
submission_id, occurred_at, event_version, evidence_status, limitations,
deduplication_key, student_visible, research_detail.

Event types (all mapped to real source records):
writing_submitted, revision_submitted, analysis_completed, feedback_available,
feedback_priority_available, feedback_without_priority (suppressed feedback),
insufficient_evidence (submission without analysis), practice_available,
exercise_attempted, practice_evaluation_recorded,
within_task_response_observed, later_task_evidence.

### 4.2 Journey API

`GET /api/v1/students/{student_id}/journey` returns
`{student_id, learner_found, counts, events[], derived_states[], state}`.
Learner not found returns the canonical 404 (resource_not_found with request
ID). State covers the empty-state taxonomy:
learner_not_found, no_submissions, submission_without_analysis,
analysis_without_priority, feedback_no_practice_target, target_no_attempt,
attempt_no_revision, revision_no_response, journey_events.

### 4.3 UI (minimal, journey-scoped)

- Student Learning Journey: loading state, accurate classified empty states,
  chronological events with localized titles/descriptions and limitation
  notices, next-action hints, no raw keys.
- Student Home: latest status + next action derived from the journey endpoint
  (replaces the empty engagement-trace dependency; reduces 3 API calls to 1).
- Research Learning Process: adds the journey event trace with source IDs
  (read-only) and lists practice records for traceability.
- Student ID: shared normalization (trim whitespace; no silent fallback; no
  auto-creation) and learner-context sync across Student pages; switching
  learners clears learner-scoped session state.
- Practice: existing exercise instance for the target is reused (no duplicate
  instance on refresh); attempts and evaluations loaded from persisted state;
  evaluation result shown after a valid attempt.
- Practice evaluation wiring: valid exercise attempts are evaluated with the
  existing conservative rule-based evaluator and persisted (no new claims).

### 4.4 Deterministic demo workflow

`scripts/demo_journey.py --setup|--status|--cleanup`:
synthetic learner `DEMO-001` (is_synthetic=1), normal service/API pathways,
local provider only, idempotent setup (existing records detected by
deduplication keys), cleanup scoped exclusively to DEMO-001 records, never
runs at application startup, prints no secrets.

### 4.5 Database and migration boundary

No migration. Migration remains 12. No schema change. No structured Journey
data is encoded into free-text fields.
