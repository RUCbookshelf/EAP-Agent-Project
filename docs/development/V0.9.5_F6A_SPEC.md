# v0.9.5-F6A Specification — RevisionService Runtime Repository Narrowing

**Date:** 2026-08-02
**Status:** ACTIVE
**Baseline:** `b4d37af` (v0.9.5-F6A0 verification); F2-F5B and F6A0 commits
are ancestors. Branch `master`, HEAD `b4d37af`.
**Prerequisite:** v0.9.5-F6A0 (implementations `693ff48`, verification
`b4d37af`) is approved and authoritative: `SQLiteRevisionRepository` now
structurally satisfies the unchanged central `RevisionRepository`;
`get_submission_bundle` and `get_latest_analysis_run` are present; the
facade-owned Submission and Analysis repositories are wired as its readers;
all repositories share the existing facade-owned connection manager; no
second repository graph was created; Revision SQL, write methods, and
transaction boundaries remain unchanged. The original blocker
(`docs/development/BLOCKER_REPORT_V0.9.5_F6A.md`) is resolved by that
prerequisite.

## Objective

Behavior-preserving runtime dependency and composition refactor. Stop
supplying the broad 86-method `Database` facade as the runtime repository of
`RevisionService`; supply the existing facade-owned `SQLiteRevisionRepository`
instance at every active direct and indirect construction path. Preserve the
existing `RevisionRepository` structural contract, all Revision behavior,
the three-sequential-commit relationship workflow, and the existing internal
composition of `SQLiteRevisionRepository`.

## 8. Three-commit transaction contract

```text
create_revision_group  → commit 1 (own connection)
link_revision          → commit 2 (own connection)
save_revision_snapshot → commit 3 (own connection)
```

The sequence is preserved exactly: no combination into one transaction, no
Unit of Work, no rollback compensation, no retries, no reordering, no
exception suppression. If commit 2 or 3 fails, the state left by the
completed earlier commits is preserved; failure semantics must not become
atomic.

## 9. Essay-update ownership

The Essay update stays inside `create_revision_group` (group row + essay
update in one connection) and inside `link_revision` (essay update + group
metadata in one connection). Neither is moved to `RevisionService`,
`SubmissionService`, a Router, a new repository, or a transaction
coordinator; neither repository method is modified.

## 10. Factory compatibility decision

`build_submission_service` gains a required keyword-only parameter
`revision_repository: RevisionRepository`. No fallback to the broad
`repository` argument is added: every active caller (production, scripts,
tests, verification helper) can pass the existing facade-owned
`_revision_repository` instance, so the permitted temporary-fallback rule
does not apply. `SubmissionService`'s public constructor, workflow, and
persistence dependencies are unchanged.

## 11. Admin Reanalysis composition decision

`AdminReanalysisService.__init__` gains a required keyword-only parameter
`revision_repository: RevisionRepository`; the embedded
`self.revisions = RevisionService(revision_repository)` uses it. The
composition root supplies `repository._revision_repository`. No private
facade access is introduced inside `AdminReanalysisService`; its own broad
repository dependency and all public methods/behavior are unchanged.

## 12. FeedbackPipeline composition decision

The authorized legacy composition line changes to
`RevisionService(self.database._revision_repository)`. The public
`FeedbackPipeline` constructor, default Database creation, initialization,
version recording, workflow order, Submission behavior, Learner Profile
behavior, return values, persistence, provider behavior, and exception
behavior are unchanged. No second repository graph is constructed.

## 14. Focused test plan

Identity: every active construction path yields
`RevisionService.repository is repository._revision_repository` (exact
instance), is not the facade, shares the facade connection manager, and uses
the already-composed readers; both application paths equivalent; no second
`SQLiteRevisionRepository` instantiation.

Behavior: Submission Bundle lookup, candidate listing, relationship
creation, Revision Group creation/linkage/retrieval, latest Analysis Run
lookup, snapshot save/list/latest, missing Submission/Analysis, invalid
relationship, empty states, ordering, relevant Revision API endpoints,
Submission factory integration, Admin Reanalysis integration,
FeedbackPipeline integration, both application-construction paths.

Transaction/failure injection (repository-level, real database): successful
creation calls `create_revision_group`, `link_revision`,
`save_revision_snapshot` in order; each is a separate repository call;
commit 1 remains visible if call 2 fails; commits 1 and 2 remain visible if
call 3 fails; no rollback compensation; no shared transaction; Essay updates
stay inside `create_revision_group`/`link_revision`; successful result
unchanged.

## 15. Database-isolation plan

Every write-capable run uses `PYTHON_DOTENV_DISABLED=1`, `DATABASE_URL`
absent, `DATABASE_PATH` set to a fresh unique temporary database,
`LLM_PROVIDER=local`, resolved-path assertions, and cleanup. The development
database SHA-256, size, and mtime are compared before and after every run
and must be unchanged; it is never opened. Ports 8000/8501 are verified free
afterward.

## 16. Rollback plan

The two focused commits (`refactor(v0.9.5-f6a): ...`, then
`test(v0.9.5-f6a): ...`) are independently revertible; no repository, SQL,
schema, or data migration is touched, so no database rollback is required.

## 17. Stop conditions

Stop and create `docs/development/BLOCKER_REPORT_V0.9.5_F6A.md` if completion
requires changing `SQLiteRevisionRepository`, either internal reader, SQL,
transaction boundaries, `RevisionRepository`, creating a new Revision Port,
narrowing SubmissionService or AdminReanalysisService persistence,
adding a fallback inside `RevisionService`, a proxy/Service Locator/DI
framework, API path/schema changes, opening or writing the development
database, or beginning F6B or a later stage. Also stop if an active
production RevisionService cannot receive the existing facade-owned Revision
repository, an active caller requires unrelated facade methods, or behavior
preservation requires a new cross-repository transaction.
