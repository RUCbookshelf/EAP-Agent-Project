# v0.9.5-F6A0 Specification — Revision Repository Capability Completion

**Date:** 2026-08-02
**Status:** ACTIVE
**Baseline:** `b766284` (v0.9.5-F5B verification); F2-F5B commits are
ancestors. HEAD `b766284`, branch `master`.
**Authorization:** Owner decision 2026-08-02 — Option C of
`docs/development/BLOCKER_REPORT_V0.9.5_F6A.md`. v0.9.5-F6A remains
formally blocked; this stage only prepares the repository capability
prerequisite.

## Purpose

Make the existing facade-owned `SQLiteRevisionRepository` structurally
satisfy the existing central `RevisionRepository` contract before any F6A
runtime narrowing is authorized. The Phase 0 source findings are
authoritative: `SQLiteRevisionRepository` does not currently expose
`get_submission_bundle` or `get_latest_analysis_run`, the facade-owned
Analysis reader is not wired into it, and the F1 audit statement that the
repository was already fully composed was incorrect.

## Required outcome

```text
Database
├── SQLiteSubmissionRepository
├── SQLiteAnalysisRepository
└── SQLiteRevisionRepository
      ├── same SQLiteConnectionManager
      ├── existing facade-owned Submission repository as bundle reader
      └── existing facade-owned Analysis repository as analysis-run reader
```

`SQLiteRevisionRepository` exposes:

```text
get_submission_bundle
get_latest_analysis_run
```

with the exact signatures required by
`app/repositories/protocols.py::RevisionRepository`.

## Implementation rules

1. Add only the two missing read capabilities.
2. Both methods are direct delegation to the injected readers; no SQL is
   duplicated or moved into `SQLiteRevisionRepository`.
3. No new connection is opened inside either delegation method (each
   delegated repository keeps its own existing connection behavior).
4. No commits, rollbacks, retries, caching, fallback logic, or exception
   translation.
5. Delegate behavior is preserved for missing records, returned
   dictionaries, exceptions, connection ownership, and transactions.
6. Wire the existing facade-owned `SQLiteSubmissionRepository` and
   `SQLiteAnalysisRepository` into the existing facade-owned
   `SQLiteRevisionRepository`; all three share the same
   `SQLiteConnectionManager`.
7. No second `Database`, connection manager, Submission/Analysis/Revision
   repository, adapter, proxy, Service Locator, or Unit of Work is
   constructed.

## Transaction safeguards

`create_revision_group`, `link_revision`, and `save_revision_snapshot` are
not modified. The Essay update stays inside `create_revision_group` and
`link_revision`; their connections and commits are unchanged; the
three-sequential-commit relationship workflow is unchanged; no operation
becomes more or less atomic. The two new read delegations add no
transaction boundary.

## Focused test plan

1. `SQLiteRevisionRepository` structurally satisfies the unchanged central
   `RevisionRepository` (every Protocol member exists with matching
   `inspect.signature`; `RevisionRepository` is not runtime-checkable, so
   the check is structural, not `isinstance`).
2. Exact signature parity of the two new methods with
   `SQLiteSubmissionRepository.get_submission_bundle` and
   `SQLiteAnalysisRepository.get_latest_analysis_run`.
3. `get_submission_bundle` delegates exactly once to the injected
   Submission reader.
4. `get_latest_analysis_run` delegates exactly once to the injected
   Analysis reader.
5. Arguments and return values pass through unchanged.
6. Missing-record behavior unchanged (None passthrough).
7. Reader exceptions propagate unchanged.
8. The facade-owned Revision repository receives the exact facade-owned
   Submission and Analysis repository instances.
9. All three repositories share the same connection manager.
10. Creating one `Database` creates only one repository graph.
11. No additional connection is opened by either delegation method (source
    scan: no `connect(` inside the two methods; stub-reader test).
12. Existing Revision write behavior and transaction tests unchanged.
13. `Database` public facade remains exactly 86 methods.

## Database-isolation plan

Every write-capable run uses `PYTHON_DOTENV_DISABLED=1`, `DATABASE_URL`
absent, `DATABASE_PATH` set to a fresh unique temporary database,
`LLM_PROVIDER=local`, resolved-path assertions, and cleanup. The
development database SHA-256, size, and mtime are compared before and after
every run and must be unchanged; it is never opened. Ports 8000/8501 are
verified free afterward.

`test(v0.9.5-f6a0): ...`) are independently revertible; no SQL, schema, data
migration, or domain behavior is touched, so no database rollback is
required.
