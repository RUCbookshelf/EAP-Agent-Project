# V0.9.6-A SPEC - Linked Revision Submission Reliability

**Status:** approved baseline `a5459e3` (v0.9.5-H2E architecture freeze).

## 1. User-visible defect

A user submitted a linked revision in the Streamlit Student Revision page. The
request took a long time and the UI eventually showed:

```text
The request took too long and was stopped. Please try again. (while submit)
```

Incident window: 2026-08-03 16:30-16:40 +08:00.

## 2. Incident classification (Phase 0 evidence)

Read-only development-database inspection (SQLite `mode=ro`, fingerprint
unchanged by the inspection) classified the incident as **C - complete linked
revision created after the UI timeout**:

- Essay 26 (student S02, revision of essay 25, group RG000005, sequence 3)
  was durably created with revision snapshot RS000012, analysis run
  AR000025, diagnosis, learner history, and feedback record 25
  (`fallback_success`) ending 08:34:04 UTC = 16:34:04 +08:00 - exactly the
  development-database mtime.
- The slow operation was the provider feedback call (`router.generate`):
  deepseek 30.4-37.7 s before fallback in the incident rows.
- Essays 24 and 25 are byte-identical linked revisions (same parent 13, same
  sequence 2, same text SHA-256) created 37 s apart - evidence that a
  duplicate POST occurred in the same window (timeout -> misleading retry ->
  second POST).

No repair was performed on incident records.

## 3. Exact timeout source

Frontend API client only:

- `app/ui/api_client.py::WritingFeedbackApiClient.submit` -> POST
  `/api/v1/submissions` with `DEFAULT_TIMEOUTS`; POST timeout tuple
  `(connect=2.0, write=30.0)`.
- `requests.exceptions.ReadTimeout` -> `ErrorCategory.REQUEST_TIMEOUT`
  (`error_request_timeout` = "The request took too long and was stopped.
  Please try again.") plus `error_operation_suffix` "(while submit)".
- `render_api_error` additionally renders a Retry button for retryable
  categories - a blind-retry instruction on a non-idempotent POST.

Not a server error; the FastAPI sync endpoint keeps running and commits after
the client disconnect (write order: essay, analysis, diagnosis, calibration,
revision relationship, history, profile are saved before
`router.generate`; feedback and history are saved after it).

## 4. Deterministic reproduction (Phase 2)

`verification/v0.9.6-a/reproduce_before.py` (real local HTTP server, fresh
temporary database, `LLM_PROVIDER=local` with a controlled slow wrapper):

- Case 1 normal completion: 0.203 s, 1 POST, 1 revision.
- Case 2 old-timeout reproduction: client write timeout 3.0 s vs controlled
  6.0 s provider -> `request_timeout` after 3.031 s, POST count 1.
- Case 3 backend after client timeout: backend completed 3.297 s after the
  client timeout with essay + revision group/snapshot + feedback - exactly
  classification C.
- Case 4 duplicate POSTs: two identical sequential POSTs created two
  byte-identical linked revisions (same parent, same text hash) - the
  incident 24/25 mechanism.

`verification/v0.9.6-a/ui_reproduce_before.py` (Streamlit AppTest, scripted
fake client): after the timeout error is displayed, a second click issues a
second POST (count 1 -> 2), and the Retry button is rendered.

## 5. Chosen bounded design

1. **Dedicated long-operation timeout**: `LONG_SUBMIT_TIMEOUTS =
   TimeoutProfile(connect=2.0, read=180.0, write=180.0)` defined once in
   `app/ui/api_client.py`; a new client method `submit_linked_revision`
   posts the same endpoint with this profile. 180 s is within the approved
   300 s cap and far above the measured 30-38 s provider calls. Ordinary
   requests (including `submit()` and all GETs) keep `DEFAULT_TIMEOUTS`.
2. **No automatic retry**: the POST is never auto-retried (unchanged
   `_request` rule: retry only ever applies to GET); the new method passes no
   retry flag.
3. **Pending state and submit locking**: session-state flag
   `revision_submit_pending` is set before the POST; the page shows the
   localized processing message; a rerun that delivers a queued second click
   is consumed by the guard (no second POST) and renders the pending/outcome
   message; the guard clears after success, a rendered outcome, or an
   ordinary error.
4. **Bounded read-only reconciliation** (only after a final client timeout,
   only existing GET APIs, at most two short calls, never recursive, never
   POSTed):
   - baseline: newest server `submitted_at` for `revision_of_submission_id ==
     source` captured at page render (server timestamps, no client clock);
   - re-fetch `GET /api/v1/students/{student_id}/revision-candidates`;
   - exact match: `revision_of_submission_id == source` and `submitted_at >
     baseline`; newest row is the submission created by this attempt;
   - then `GET /api/v1/submissions/{essay_id}`: `feedback` present ->
     CONFIRMED_SUCCESS; essay present without feedback -> STILL_PROCESSING;
   - no match or reconciliation read failure -> UNCONFIRMED.
5. **Accurate localized messages** (en + zh_CN, parity preserved):
   - pending: "Submitting and analyzing the linked revision. This may take a
     few minutes."
   - CONFIRMED_SUCCESS: "The linked revision was submitted successfully."
   - STILL_PROCESSING: "The request took longer than expected, but the linked
     revision is still being processed. Check the revision history before
     submitting it again."
   - UNCONFIRMED: "The request timed out before the result could be
     confirmed. The submission may still have been received. Check the
     revision history before trying again."
   No raw exceptions, provider names, or stack traces; no blind "try again"
   instruction on the timeout path.

## 6. Scope

Production changes (proven necessary by the source trace):

```text
app/ui/api_client.py                      (LONG_SUBMIT_TIMEOUTS + submit_linked_revision)
app/ui/ports/student.py                   (StudentRevisionApiPort.submit_linked_revision)
app/ui/features/student/revision.py       (pending guard, timeout handling, reconciliation, messages)
locales/en.json, locales/zh_CN.json       (four new keys each)
```

Backend changes: none. No Repository, SQL, schema, migration, transaction
boundary, analysis, prompt, provider, Router, or Service change.

## 7. Focused tests

`tests/test_v096a_linked_revision_submission.py` plus a reusable AppTest
harness: dedicated timeout used; generic timeout unchanged; exactly one POST;
no automatic retry after ambiguous timeout; guard holds during processing and
releases after terminal states; controlled slow completion below the new
timeout succeeds; timeout reconciliation (confirmed success / still
processing / unconfirmed); no blind-retry instruction; linked-revision
identity and parent/group linkage; no duplicate revision in the controlled
timeout case; en/zh locale parity; original non-linked `submit()` unchanged.

## 8. Acceptance criteria

As authorized: dedicated bounded timeout (180 s), ordinary timeouts
unchanged, visible pending state, no duplicate POST while pending, no
automatic POST retry, controlled slow linked revision succeeds, timeout
reconciliation uses only exact available evidence, confirmed backend success
shown as success, unconfirmed result never shown as definite failure, no
immediate blind resubmission recommendation, linkage preserved, no duplicate
revision in controlled tests, locale parity, focused tests, targeted
user-flow verification, full non-live core exit 0, exact
`cmd /c "run.bat --verify"` PASS, API/database/migration/architecture
invariants unchanged, development database unchanged, research exports
restored to the exact baseline.

## 9. Stop conditions

Blocker report `docs/development/BLOCKER_REPORT_V0.9.6_A.md` if the path
cannot be identified, the timeout cannot be reproduced, the incident cannot
be classified and reproduction fails, a POST retry layer cannot be safely
disabled, controlled completion exceeds 300 s, a queue/migration/new durable
job table is required, exact reconciliation requires weak matching,
transaction boundaries must change, the development database changes during
read-only inspection, a baseline export is modified/deleted, or unrelated
architecture work is required.
