## 2. Current real workflow (evidence, not filenames)

### 2.1 Where priorities are stored

- Persisted structured feedback: `feedback_records.feedback_json.priority_feedback` (`app/models/schemas.py:173-179` - `FeedbackItem`: `diagnosis_id`, `category`, `evidence_quote`, `explanation`, `revision_guidance`), written by `SubmissionService.submit` at `app/services/submission.py:204` and read back inside the submission bundle at `app/infrastructure/sqlite/repositories/submission.py:151-178`.
- Diagnosis records: `diagnoses.diagnosis_json.improvement_priorities` (`app/models/schemas.py:121-123`).
- Practice targets: `practice_targets` table (`app/database/migrations.py:677`); rows are created only by an explicit `POST /api/v1/practice-targets` (`app/api/routers/practice.py:27-42`); no production component auto-creates targets from generated priorities (confirmed by D0-R `verification/v0.9.6-d0-r/downstream_consumability.json`: `practice_targets_auto_created: false`).
- There is no dedicated "active priority" record. The authoritative active priority for a source essay is the persisted `feedback.priority_feedback` of that essay.

### 2.2 How Feedback selects and transfers a priority

- The Feedback page renders only the in-session result (`st.session_state["submission_result"]`), guarded per learner by `_writing_saved_for_learner` (`app/ui/features/student/session.py:8-12`); with no session result it shows "No feedback in this session" (`app/ui/features/student/feedback.py:123-134`).
- With a priority: up to two `feedback_priority_card` instances are rendered (`feedback.py:72-78`) and the only action is "Open Practice" (`feedback.py:139-145`), which navigates to Practice - where, with no auto-created target, the student sees "No active practice target is available" (`app/ui/features/student/practice.py:112-133`). There is no Feedback-to-Revision transfer when a priority exists.
- No priority: explicit "Revise This Draft" (to Writing revision mode via `_navigate_writing_revision`, `app/ui/features/student/navigation.py:18-29`) and "Finish This Feedback Cycle" (`navigation.py:31-43`).
- Selection: no mechanism selects one of several priorities; the page simply renders the first two cards (`feedback.py:74`).

### 2.3 How Revision obtains essay, feedback, and priority

- In-session path: the just-submitted `submission_result` (`app/ui/features/student/revision.py:76-111`).
- Fresh path (refresh, direct navigation, Home CTA): candidates selectbox over `GET /api/v1/students/{id}/revision-candidates` (`revision.py:112-133`; rows from `app/infrastructure/sqlite/repositories/submission.py:182-199`), then `get_submission(source_id)` (bundle with persisted feedback) and `get_practice_targets(learner_id)` (`revision.py:135-139`).
- The priority is not displayed in the fresh path: the bundle's `priority_feedback` is only checked for presence to decide whether to show a "no automatic focus" note (`revision.py:142-149`); a matching practice target label is shown only if a target exists (`revision.py:151-159`).
- Home already routes journey state `feedback_no_practice_target` to "Open Revision" (`app/ui/features/student/home.py:34-41`), i.e. the fresh path.

### 2.4 What is persisted on revision submission

- The Revision page posts one `submit_linked_revision` request to `POST /api/v1/submissions` with `revision_of_submission_id` = source essay id (`revision.py:196-222`; `app/ui/api_client.py:228-230`; router `app/api/routers/submissions.py:21-42`).
- `SubmissionService.submit` validates the relationship and cross-student rule (`app/services/submission.py:116-121`; `app/services/revision.py:20-45`), saves the new essay, runs analysis/diagnosis/calibration, creates the revision group and snapshot (`app/services/submission.py:157-160`), generates and persists feedback (`submission.py:204`), and returns the trajectory.
- No priority field is sent or persisted on the revision row; the addressed priority is derived from the source's persisted feedback.

### 2.5 Post-submission state and next step

- After success the page stores `submission_result` and reruns (`revision.py:203-238`); the saved state shows original context, a success box, the conservative observation (including "Previous Feedback Focus" from `within_task_revision_trajectory.previous_selected_priorities`, `revision.py:90-105`), and a single "Open Learning Journey" button (`revision.py:106-110`).
- There is no explicit priority-addressed confirmation, no identifiable revision record beyond a technical caption, no end-of-cycle action (Home / Writing / Feedback), and no Practice continuation entry.
- Re-entry in a fresh session shows the submission form again for the source; the existing revision is not detected, so the workflow can be treated as unsubmitted and an uncontrolled second revision can be created.

### 2.6 Practice entry point

- Safe and reusable: `render_practice_page` consumes active targets when they exist and reports the missing-target state accurately without fabricating anything (`app/ui/features/student/practice.py:112-133`).

## 3. Confirmed gaps (SPEC section 3 and D0-R findings)

- G1: No Feedback-to-Revision transfer when a priority exists (`feedback.py:139-145`).
- G2: The active priority is not displayed on the Revision page's fresh-source view (`revision.py:142-159`); D0-R classification PARTIALLY_CONSUMABLE: "the selected priority family is not re-displayed on the fresh-source Revision view".
- G3: No explicit active-priority selection mechanism when several priorities exist (`feedback.py:74`, `revision.py:142-149`).
- G4: Post-submission state is ambiguous: no priority-addressed confirmation, no identifiable record, no end-of-cycle path, no Practice continuation (`revision.py:106-110`).
- G5: Re-entry after refresh treats the revision as unsubmitted (no existing revision detection; duplicate-submission risk in a new session).
- G6: Feedback copy implies a priority-specific practice activity exists ("Use the selected priority to complete one focused activity on the Practice page", `student_feedback_next_practice`), while no target is auto-created - misleading per SPEC section 4.D.

## 4. Frozen change scope (UI + session state only)

No database migration, schema, API, domain-model, service, or prompt change is required: the persisted source `feedback.priority_feedback` already contains every priority field (category, explanation, evidence quote, revision guidance), the linked-revision submission already persists the revision and builds the within-task trajectory, and the server already rejects cross-student / cross-essay associations (`app/services/revision.py:20-45`). If a later work unit demonstrates that a UI-only change cannot satisfy an acceptance criterion, implementation stops and the finding is reported with evidence before any scope change.

### D1 - Active priority definition and transfer (Work Unit 2)

- Authoritative source: the selected source essay's persisted structured feedback `priority_feedback` (read through the existing submission bundle). No second copy is created; session state carries only a selection reference.
- Transfer: new helper `_navigate_priority_revision(source_id, lang)` in `navigation.py` sets `revision_source_preset` (source essay id) and clears stale revision presets, then navigates to the Revision page (mirrors the existing `_navigate_writing_revision` pattern, `navigation.py:18-29`).
- Selection: if the source has more than one priority, the Revision page shows a stable-keyed radio ("Which priority do you want to address?") defaulting to the first; the chosen index is kept in `st.session_state["revision_priority_selection"]` = `{submission_id, index}`.
- Recovery: on rerun the selection is revalidated against the bundle; a stale or invalid index falls back to the first priority with a short explanatory note; on refresh the selection defaults to the first priority (documented behavior); missing or malformed `priority_feedback` degrades to the existing accurate no-auto-focus flow.

### D2 - Feedback page (Work Unit 2)

- Priority branch: primary action "Open Revision" (priority-guided revision) plus secondary "Open Practice" with accurate copy: navigating to Practice only uses existing targets; targets are not auto-created from this priority. No-priority branch unchanged.

### D3 - Revision page priority context (Work Unit 2)

- Preset consumption: `revision_source_preset` preselects the source in the candidate list (validated against the current learner's candidates); direct navigation keeps the selectbox.
- Priority task section (fresh and session paths): category label, explanation (the problem), evidence quote ("From Your Writing"), revision guidance (direction), the original text, and a clear revision instruction - rendered from the persisted bundle fields with existing pixel components.

### D4 - Revision submission loop (Work Unit 3)

- Unchanged submission payload and reliability guards (pending guard, bounded reconciliation, saved-state lock - `revision.py:186-202`); empty-text validation unchanged; no API or service change.

### D5 - Completion state and next steps (Work Unit 4)

- Completion state adds: explicit "revision saved" confirmation; "priority addressed" block from `within_task_revision_trajectory.previous_selected_priorities` (the submission response's persisted-derived record) or the source bundle; the revision record reference (submission id); "current revision step complete".
- Outcomes:
  - End cycle: "Finish This Revision Cycle" - acknowledges the finished revision in-session, clears the stale saved panel and presets, returns to a fresh Home (or Writing) state; never deletes or resubmits.
  - Continue learning: "Open Practice" with the accurate note that priority-specific practice targets are not auto-generated in this version.
  - "Open Learning Journey" retained.

### D6 - Re-entry and boundary handling (Work Unit 4)

- If a revision of the selected source already exists (newest candidate with `revision_of_submission_id == source_id`), the Revision page shows the completed state (priority addressed, revision record reference, next steps) instead of a blank form - the revision is never treated as unsubmitted on re-entry and no uncontrolled duplicate can be created from the page.
- Missing candidate / no feedback / no priority / provider / database errors: existing accurate empty states, `render_api_error`, and limitation notices; no blank page or uncaught exception.
