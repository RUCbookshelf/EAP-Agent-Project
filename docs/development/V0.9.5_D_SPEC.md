## 2. Shared client methods appearing in multiple Ports

`get_journey` (Home, Journey, Learning Process); `get_practice_targets` (Home, Practice, Revision, Learning Process); `get_student_revision_candidates` (Writing, Feedback, Revision); `submit` (Writing, Revision); `get_submission` (Revision, Evidence); `get_diagnostic_audit` (Evidence, System Audit); `research_data_quality` (Overview, Data). Ports describe consumer requirements, so sharing is intentional.

## 3. Concrete-client structural-conformance strategy

- `WritingFeedbackApiClient` remains the single concrete HTTP client; no per-feature wrappers/proxies, no DI framework.
- Each Port is a `typing.Protocol` declaring exactly the methods above with the concrete client's argument names/order/defaults and conservative frontend-safe return annotations (`dict[str, Any]`, `list[dict[str, Any]]`, `Any`).
- Feature renderers and feature helpers that accept an API client are annotated with their Port; the client parameter keeps the name `api_client`.
- `WritingFeedbackApiClient` satisfies all Ports structurally (static test verifies every Port method exists on it with a compatible signature).
- `streamlit_app.py` wiring is unchanged.

## 4. Endpoint/client/feature classification rules

- Every one of the 77 path+method contracts is classified exactly one of: `A. wrapped_and_used`, `B. wrapped_but_currently_unused`, `C. intentionally_unwrapped` (with a reason: backend-internal / admin-only / API-debug-inspection / not-part-of-current-Streamlit-product / future-feature / accessed-through-aggregate-endpoint).
- Every public client method is classified exactly one of: `A. used_by_one_or_more_features`, `B. intentionally_unused_but_retained`, `C. obsolete_or_unmapped_candidate` (documented status; nothing deleted).
- The approved contract lives in `tests/contracts/api_surface_contract.py`; the machine-readable evidence JSON lives under `verification/v0.9.5-d/`.
- Enforcement tests: endpoints may not appear/disappear or change classification without updating the contract; client methods may not gain/lose wrappers silently; feature calls must be owned by the feature's Port; a Student feature may not gain Research/Admin methods; a Research feature may not gain unrelated Student write methods; no unclassified additions.

## 5. Practice and Research parity rules

- Production `app/ui` stays independent of `app.practice.*` and `app.research.schemas`.
- Practice parity test compares the UI contract against the backend authoritative `default_exercise_specifications()` for every supported exercise type: English and Chinese learner instructions, stable identifiers, fallback behavior. No evaluation/target-selection/progression logic moves into the UI.
- Research export parity test compares `build_export_job_payload()` against backend `ExportJob(...).model_dump(mode="json")` for every privacy mode × format combination, single- and multi-format, default filter structure, enum strings, absent-vs-default fields, UTC timestamp format, and exact JSON key structure.

## 6. Compatibility-facade migration rule

- Compatibility exports in `app/ui/pages/student_pages.py` and `research_pages.py` are retained (including private-helper aliases); deprecation comments mark them compatibility-only, with no runtime warnings.
- Repository tests that import private helpers from the facades migrate to the true feature-owner modules.
- One explicit compatibility-resolution test (`tests/test_v095c_feature_extraction.py::test_private_helpers_remain_importable_from_facade`) remains; a static test prohibits any new private-helper facade import in production or tests outside that documented allow-list.
