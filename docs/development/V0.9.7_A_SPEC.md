## 2. Primary Goal

Complete the currently incomplete priority-guided revision workflow so that a student can move through the following full cycle:

```text
Writing
→ Feedback
→ Select or confirm a naturally generated priority
→ Priority-guided Revision
→ Submit the revision
→ Receive a clear completion result and next step
→ Safely end the learning cycle or continue to an existing Practice entry point
```

The purpose of this phase is not to generate more feedback. The purpose is to ensure that an already generated priority can drive a complete, understandable, persistent, recoverable, and safely terminable student revision workflow.

At the end of the workflow, the student must clearly understand:

1. Which priority they are currently addressing.
2. Why that priority was selected.
3. What type of revision they are expected to make.
4. Whether their revision was successfully submitted.
5. What state the current learning cycle is now in.
6. What they can do next.
7. How to safely leave or complete the workflow.

## 4. Strict Scope

This phase must complete the following work.

### A. Audit the Current Real Workflow

Before changing implementation, inspect the actual code, persistence model, page state, and tests to reconstruct the real current workflow:

```text
Feedback priority
→ Revision page
→ Revision input
→ Revision submission
→ Persistence
→ Post-submission state
→ Journey or subsequent page
```

Determine and document:

- where priorities are currently stored;
- how the Feedback page selects or transfers a priority;
- how the Revision page currently obtains the essay, feedback, and priority;
- which fields are persisted when a revision is submitted;
- whether refresh, rerun, back navigation, direct navigation, repeated submission, or lost session state can break the workflow;
- why the post-submission state currently lacks a clear next step;
- whether the existing Practice page has a safe, reusable entry point.

Do not infer behavior from filenames alone. Support the workflow analysis with concrete `file:line` evidence.

### B. Establish a Clear Priority-Guided Revision Context

When entering Revision, the student must be able to see and understand:

- the current priority title or concise label;
- the problem represented by the priority;
- the relevant source-text evidence or feedback evidence;
- the recommended revision direction;
- the essay or text currently being revised;
- a clear revision instruction.

Prefer existing structured feedback, schemas, domain objects, and persisted records.

Do not reconstruct priorities by parsing rendered page text.

Do not create multiple inconsistent copies of the same priority across pages.

If the system supports multiple priorities, implement the smallest reliable mechanism for one active priority.

Define explicitly:

- how the active priority is selected;
- how it is transferred between pages;
- how it is restored after a rerun or refresh;
- how the system behaves when no priority exists;
- how the system safely degrades when priority data is missing, stale, malformed, or invalid.

### C. Complete the Revision Submission Loop

The Revision page must support one explicit and reliable submission action.

Before persistence, perform all necessary validation, including at minimum:

- revision text must not be empty;
- the revision must be linked to the correct essay or revision task;
- the current student, essay, feedback, and priority must belong to the same valid context;
- a revision must never be linked to another student's data;
- repeated clicks or Streamlit reruns must not create uncontrolled duplicate records.

After a successful submission, display a clear completion state containing:

- confirmation that the revision was successfully saved;
- the priority addressed by this revision;
- an identifiable revision record or status;
- confirmation that the current revision step is complete;
- clear next-step actions.

If submission fails:

- do not display a false success state;
- preserve the student's entered revision text;
- show an understandable and recoverable error message;
- do not lose or corrupt existing essay, feedback, or revision data.

### D. Implement a Clear Post-Submission Next Step

After a successful revision submission, the interface must not remain in an ambiguous state.

Provide at least two semantically clear outcomes.

#### Outcome 1: End the Current Revision Cycle

The interface must:

- state that the current priority-guided revision has been completed;
- allow the student to safely return to Feedback, Writing, or the Student home page;
- avoid treating the revision as unsubmitted when the student later re-enters the workflow.

#### Outcome 2: Continue Learning

If the existing Practice route can be safely reused, provide a clear entry point to that existing Practice page or workflow.

If the current Practice system cannot reliably consume the active priority:

- present an accurate, non-misleading continuation message;
- do not pretend that a priority-specific practice task has already been generated;
- do not implement automatic Priority-to-Practice target generation in this phase.

The interface must not blur the distinction between:

- navigating to an existing Practice capability; and
- automatically generating a practice target from the current priority.

### E. Handle State Recovery and Boundary Conditions

At minimum, handle and verify the following scenarios:

- no essay exists;
- an essay exists but no feedback exists;
- feedback exists but no priority exists;
- priority data is missing or invalid;
- direct navigation to the Revision page;
- normal navigation from Feedback to Revision;
- Revision page refresh or Streamlit rerun;
- locale switching;
- sidebar opening and closing;
- successful submission followed by a rerun;
- repeated submission clicks;
- returning to Feedback after submission;
- re-entering Revision after submission;
- provider errors;
- database errors;
- mismatched student IDs;
- mismatched essay, feedback, or priority associations.

Every exceptional state must fail safely and explain itself clearly.

The application must not produce:

- a blank page;
- an uncaught exception;
- a false success message;
- duplicate uncontrolled records;
- data loss;
- cross-student data association.
