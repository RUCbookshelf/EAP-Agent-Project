# v0.9.5-F5A Specification — CALF Service Dependency Narrowing

**Date:** 2026-08-02
**Status:** ACTIVE
**Baseline:** `80be7f3` (v0.9.5-F4 verification); F2 `7927ca7`, F3
`a24312a`/`256b172`, and F4 `bb0c348`/`80be7f3` are ancestors.

## Objective

Behavior-preserving Service dependency refactor. Replace the broad, untyped
persistence dependency of `CalfService` with four explicit consumer-owned
structural Ports and supply the existing facade-owned CALF, Submission,
Analysis, and Learner repository instances through the application
composition root. Preserve all CALF report, trajectory, annotation-read, and
annotation-import behavior and the existing per-method SQLite transaction
behavior. No other Service, router workflow, repository implementation, SQL
statement, API contract, or UI behavior changes.

## 3. Exact four Port signatures

All Ports are `typing.Protocol` classes defined in `app/services/calf.py`.
Signatures, parameter names, defaults, and return annotations match the
repository implementations at HEAD `80be7f3` exactly. No inheritance from
central repository Protocols; no concrete SQLite imports; no `Database`
import; no method beyond the approved set.

`CalfDataPort`

```python
def list_analysis_units(self, submission_id: int, analysis_run_id: str | None = None) -> list[dict[str, Any]]: ...
def list_error_annotations(self, submission_id: int) -> list[ErrorAnnotation]: ...
def save_error_annotations(self, submission_id: int, annotations: list[ErrorAnnotation]) -> list[ErrorAnnotation]: ...
```

Source: `app/infrastructure/sqlite/repositories/calf.py` (`list_analysis_units`,
`list_error_annotations`, `save_error_annotations`).

`CalfSubmissionReadPort`

```python
def get_submission_bundle(self, essay_id: int) -> dict[str, Any] | None: ...

```

Source: `app/infrastructure/sqlite/repositories/submission.py`
(`get_submission_bundle`, `list_student_submissions`).

`CalfAnalysisReadPort`

```python
def get_latest_analysis_run(self, essay_id: int) -> dict[str, Any] | None: ...
```

Source: `app/infrastructure/sqlite/repositories/analysis.py`

`CalfStudentReadPort`


Source: `app/infrastructure/sqlite/repositories/learner.py` (`get_student`).

## 4. Service constructor before and after

Before:

```python
def __init__(self, repository) -> None:
    self.repository = repository
    self.registry = default_calf_registry()
```

After:

```python
def __init__(
    self,
    calf_repository: CalfDataPort,
    submission_reader: CalfSubmissionReadPort,
    analysis_reader: CalfAnalysisReadPort,
    student_reader: CalfStudentReadPort,
) -> None:
    self.calf_repository = calf_repository
    self.submission_reader = submission_reader
    self.analysis_reader = analysis_reader
    self.student_reader = student_reader
    self.registry = default_calf_registry()
```

No broad `repository` field, no untyped persistence parameter, no
compatibility fallback, no `hasattr` capability discovery, no concrete
SQLite type in the Service module, no `Database` import.

## 6. Read/write ownership

```text
get_submission_bundle, list_student_submissions → CalfSubmissionReadPort (read)
get_latest_analysis_run                        → CalfAnalysisReadPort (read)
get_student                                    → CalfStudentReadPort (read)
list_analysis_units, list_error_annotations     → CalfDataPort (read)
save_error_annotations                          → CalfDataPort (write, only CALF write)
```

No read is duplicated across Ports; no Port delegates to another inside the
Service; no caching, retries, batching, or query consolidation.

## 7. Annotation transaction-preservation rule

`save_error_annotations` remains exactly one repository-owned call to
`SQLiteCalfRepository.save_error_annotations`, including the Essay-existence
guard (inside the repository method), existing table reads used by the guard,
annotation batch persistence, connection lifetime, commit/rollback, error
behavior, and returned value. The Service never performs its own Essay
existence check before the write and never splits the operation. No shared
transaction spans Submission, CALF, Analysis, or Learner repositories; each
repository method keeps its own existing connection and transaction behavior.

## 9. Focused test plan

Ports: exact method sets; `inspect.signature` parity with the four repository
implementations; structural satisfaction of each Port by its repository and
by `Database` (legacy verification only).

Service: a minimal three-method CALF stub, two-method Submission reader,
one-method Analysis reader, and one-method Student reader are sufficient; no
unrelated repository method required; no dynamic capability discovery;
successful read/report flows preserve call order and output; missing
Submission, Student, or Analysis data preserves current behavior; successful
annotation import makes exactly one `save_error_annotations` call; validation
or pre-write failure performs zero saves; repository exceptions propagate
unchanged; no shared transaction introduced.

Composition: both app-construction paths wire the four facade-owned
repository instances by identity and same `_connection_manager`; no second
Database or repository graph; CALF router behavior unchanged.

## 10. Database-isolation plan

Every process capable of constructing `Database` runs with
`PYTHON_DOTENV_DISABLED=1`, `DATABASE_URL` removed, `DATABASE_PATH` set to a
fresh path inside a unique temporary directory, and `LLM_PROVIDER=local`; the
effective path is resolved and printed, asserted inside the temporary
directory, asserted not to be the development database or any backup, and
asserted to start in the expected fresh state. After each run, connections
and processes are closed, the temporary directory is removed, ports 8000/8501
are verified free, and the development database SHA-256, size, and mtime are
rechecked (must be unchanged; it is never opened).

## 11. Rollback plan

All changes are reversible through the two focused commits
(`refactor(v0.9.5-f5a): ...`, then `test(v0.9.5-f5a): ...`); `git revert` of
either commit restores previous behavior. No schema, SQL, or data migration
is touched, so no database rollback is required.
