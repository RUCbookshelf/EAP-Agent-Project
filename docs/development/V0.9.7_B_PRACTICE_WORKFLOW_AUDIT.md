## 2. Current data model

- Tables (migration 12, `app/database/migrations.py:677-684`): `practice_targets`,
  `exercise_instances`, `exercise_attempts`, `practice_evaluations`, `feedback_engagement_traces`,
  `within_task_response_candidates`, `transfer_evidence_candidates`, `practice_state_snapshots`.
  Every table stores the full entity JSON in a `*_json` column plus a small set of queryable
  columns; IDs are TEXT PRIMARY KEYs (`app/database/migrations.py:677`).
- `PracticeTarget` schema (`app/practice/schemas.py:37-53`): practice_target_id, student_id,
  source_submission_id, source_analysis_run_id (None), source_diagnosis_id, source_priority_id
  (optional, default None), target_code, target_label, target_scope ("within_task"), evidence_ids,
  diagnostic_gate_status ("selected"), diagnostic_version ("diagnostic-v0.6.1"),
  configuration_version ("config-v0.9.0"), status, created_at. `extra="forbid"`.
- Target ID generation: `_next_practice_id` MAX+1 per table
  (`app/infrastructure/sqlite/repositories/practice.py:12-30`) then `PT{n:06d}`
  (`practice.py:38-48`). No UUIDs, no per-student sequences.
- Status: `PracticeTargetStatus` ACTIVE / INACTIVE / PRACTICE_NOT_AVAILABLE / ARCHIVED
  (`app/practice/schemas.py:12-16`). No production code ever transitions status after creation:
  the router writes the initial ACTIVE row and no update method exists in `PracticeWritePort`
  (`app/practice/ports.py:39-52`); there is no completed/expired/superseded/abandoned state.
- Linkage to learner: `student_id` column. Linkage to source: `source_submission_id` +
  `source_diagnosis_id` columns; `source_priority_id`, `source_analysis_run_id`, and
  `evidence_ids` exist only inside `target_json` and are not SQL-queryable.
- Multiple active targets: permitted (no uniqueness constraint beyond the ID primary key).
- Tracing a target back to one exact generated priority: structurally possible
  (`source_priority_id` field) but not implemented in the API path (see section 3); no stable
  priority item identifier exists in the persisted feedback records today.
- Compatibility with a future mapping: existing rows remain valid (`target_json` is
  schema-versioned per entity; legacy DEMO row has `source_priority_id: "PRIO-18"`, a
  demo-invented reference, and `source_analysis_run_id: null` - verified in the dev DB).

## 3. Current target-creation path

- Endpoint: `POST /api/v1/practice-targets` (`app/api/routers/practice.py:27-42`) ->
  `PracticeService.create_practice_target` (`app/practice/service.py:21-41`) ->
  `SQLitePracticeRepository.save_practice_target` (`app/infrastructure/sqlite/repositories/practice.py:38-48`).
- Callers of the endpoint: no production UI (the UI feature port has no create method;
  `app/ui/ports/student.py` StudentPracticeApiPort exposes only targets read, exercise create,
  attempts, instances - the client method exists at `app/ui/api_client.py:361-362` but no page
  calls it). Callers are tests and verification fixtures:
  `tests/test_journey_v093c.py:498`, `tests/test_v095f6d_practice_boundary_narrowing.py:69`,
  `verification/v0.9.4-b/v0.9.4-b-20260801-r1/practice_slice.py` (`seed_target_via_existing_api`).
  `scripts/demo_journey.py:170-175` calls the service directly (bypasses the API).
- Router payload forwarding: the router forwards student_id, source_submission_id,
  source_diagnosis_id, target_code, target_label, gate_status only
  (`app/api/routers/practice.py:32-39`); `source_priority_id` and `evidence_ids` are dropped.
  Consequently API-created targets persist `source_priority_id: null` and `evidence_ids: []`,
  while demo-created targets (direct service call) carry them
  (`scripts/demo_journey.py:170-175`, `source_priority_id=f"PRIO-{essay_id}"`).
- Validation before creation: only `gate_status == "selected"` is enforced
  (`app/practice/service.py:23-26`). There is no `require_student` on the POST route
  (`app/api/routers/practice.py:27-28`), no existence/ownership check on `source_submission_id`,
  no check that `source_diagnosis_id` belongs to the source, and no cross-student rejection.
- Idempotency: none. Every POST inserts a new row with a fresh `PT######` id; duplicate targets
  for the same logical source are possible.
- Transactionality: service validation and repository insert are separate operations; each
  insert is atomic, but there is no transaction spanning validation + write. A rerun after a
  successful insert is not detectable by the client (no idempotency key returned/stored).
- `_next_practice_id` collision risk (direct evidence): the allocator computes
  `MAX(CAST(SUBSTR(id, 3) AS INTEGER)) + 1` (`app/infrastructure/sqlite/repositories/practice.py:16-27`).
  For 3-character prefixes (FET, WTR, PSS) `SUBSTR(id, 3)` starts at the third character
  ("T000001"/"R000001"/"S000001"), `CAST` yields 0, so the allocator returns 1 for every insert.
  Reproduced in-memory: after inserting `WTR000001`, the allocator returns 1 again and the second
  identical insert raises `sqlite3.IntegrityError: UNIQUE constraint failed`. The 2-character
  prefixes (PT, EX, EA, PE, TE) are unaffected. This is documented as a known limitation
  (`docs/KNOWN_LIMITATIONS.md:3-6`; `docs/development/CURRENT_TASK_STATE.md:696`;
  `docs/development/DECISION_LOG.md:540`). Current production impact: PT/EX/EA/PE are the only
  tables written by the API today, so target/attempt/evaluation IDs are safe; FET/WTR/PSS are
  written only by demo/tests (WTR single-row fixtures), so the bug currently affects demo/test
  multi-row scenarios, not production. Any v0.9.7-B write to those tables (e.g., engagement
  traces) requires the allocator fix first.

## 4. Current Practice entry and target-selection path

- Entry actions: Home CTA for states `target_no_attempt` / `attempt_no_evaluation` maps to
  "Open Practice" (`app/ui/features/student/home.py:38-39`); Feedback secondary button
  (`app/ui/features/student/feedback.py`, v0.9.7-A `feedback_practice_action`); Revision
  completion "Open Practice" (`app/ui/features/student/revision.py` `_render_revision_next_steps`);
  Learning Journey CTA; direct sidebar navigation; fresh sessions after refresh.
- Page flow (`app/ui/features/student/practice.py:65-284`): student_id_input -> learner guard ->
  `get_practice_targets` -> `active_targets = [t for t in targets if t.status == "active"]`
  (practice.py:103-105) -> `active_targets[0]` (practice.py:138). Repository ordering is
  `ORDER BY created_at` ascending (`app/infrastructure/sqlite/repositories/practice.py:52-55`),
  so selection is deterministic: the oldest active target.
- Multiple targets: always the oldest active one; other targets are unreachable from the page.
- No target: accurate empty state (`practice.py:121-135`) - explains no-priority cycles and
  offers "Open Writing"; no fabrication.
- Learner resolution: `student_id_input` + `set_selected_learner` (learner-scoped session state
  clearing); GET targets is `require_student`-guarded (`app/api/routers/practice.py:19-24`).
- Session state: caches `practice_targets_v2`, `current_exercise_v2`, `exercise_attempts_v2`
  (`practice.py:110-119`); no explicit target-ID selection is stored, so reruns/refreshes reload
  from the API and re-derive the same oldest-active target. Navigation cannot open an unrelated
  target through this path.
- Stale/malformed/completed/foreign targets: a deleted target disappears from the list (no
  dangling session ID); a malformed `target_json` row raises a JSON decode error in the
  repository (500; no graceful degradation); "completed" does not exist as a status; foreign
  targets are excluded by the student-scoped query.

## 5. Current practice task rendering

- With an active target but no exercise (`practice.py:142-157`): target focus label
  (`practice_target` section + `student_practice_focus`), source_submission technical caption,
  a "source text" text area the student fills, and a Generate Exercise button.
- With an exercise (`practice.py:163-212`): exercise instructions (localized via
  `exercise_instruction` contract, `app/ui/contracts/practice.py`), source_text evidence quote,
  two constraints ("Retain original meaning.", "Do not add unsupported content."), response text
  area, submit button. Step tracker: target -> exercise -> response -> evaluation.
- What is NOT shown for an active target: a learning objective, the priority explanation /
  revision guidance, completion criteria, the target status, or the priority evidence quote
  (unless it happens to be pasted as exercise source text).
- Sufficiency for a priority-derived task without changing the Feedback schema: yes - the
  persisted `feedback.priority_feedback` items plus the existing target fields
  (target_code, target_label, evidence_ids, source_priority_id) are sufficient; the missing
  pieces are mapping/translation and optional carry-through of explanation/revision_guidance
  into target/exercise display.

## 6. Current attempt and evaluation path

- UI validation: empty response shows a field error and does not POST (`practice.py:158-160`).
  Server-side minimum length is 3 non-blank characters (`app/practice/service.py:43-50`).
- API: `POST /api/v1/exercises/{exercise_id}/attempts` (`app/api/routers/practice.py:84-115`):
  exercise existence check (404); `attempt_number = len(existing_attempts) + 1`
  (practice.py:89-90); invalid input returns an INVALID_INPUT attempt that is NOT persisted
  (practice.py:92-93); valid input persists the attempt, then best-effort evaluation: target
  lookup, source text from the submission bundle (`get_submission_bundle`), rule-based
  evaluation, persisted evaluation row, attached as `attempt["evaluation"]`; any evaluation
  exception leaves `attempt["evaluation"] = None` (attempt remains authoritative) (practice.py:94-108).
- Attempt schema: `ExerciseAttempt` (`app/practice/schemas.py:105-119`): attempt_id (EA######),
  exercise_id, student_id, attempt_number, response_text, started_at, submitted_at,
  duration_seconds, timing_source, hint_count, status, created_at.
- Duplicate prevention: none at the API level (every POST inserts a new attempt with the next
  number; no pending guard, no idempotency key). The UI locks after a saved attempt
  (the attempts branch renders the saved state and no submit button, `practice.py:213-244`), but
  two rapid clicks before the rerun can produce two POSTs. This is a real gap for repeated-click
  protection.
- Cross-student prevention: the attempt POST does not verify that the payload `student_id` owns
  the exercise/target (`app/api/routers/practice.py:84-115`); cross-student attempts are possible
  through direct API use.
- Input survival on failure: `render_api_error` path; the response text area keeps its widget
  value on rerun, so input is preserved. Attempt persistence and evaluation are not wrapped in
  one transaction; evaluation failure is handled (partial attempt + explicit "evaluation
  unavailable" UI state, `practice.py:233-238`).
- Re-entry after a saved attempt: the page reloads attempts from the API
  (`practice.py:105-108`) and shows the saved response + evaluation (or the cached evaluation
  from the immediate rerun, `_practice_attempt_with_cached_evaluation`), no blank/duplicate form.

## 7. Current completion and re-entry behavior

- Completion is not persisted: target `status` stays "active"; the UI treats "an attempt
  exists" as done (success box + evaluation + "Open Revision" button, `practice.py:213-244`).
- A single submitted attempt with a persisted evaluation is the de facto completion condition;
  evaluation failure still locks the saved-response state with an explicit unavailable notice.
- No explicit finish action and no safe continuation path to another existing target (the page
  always selects the oldest active target, which is the one just practiced).
- Journey state after attempt + evaluation advances to `revision_no_response`
  (`app/journey/service.py:472-479`), so Home points back to Revision; a target never becomes
  "completed" for Journey purposes.
- Re-entry after refresh: deterministic reload; the saved result is displayed; no duplicate
  form.

## 10. `_next_practice_id` collision analysis

- Mechanism: per-table `MAX(CAST(SUBSTR(id, 3) AS INTEGER)) + 1`
  (`app/infrastructure/sqlite/repositories/practice.py:16-27`), allocated before each INSERT in
  a separate connection context, with the ID column as PRIMARY KEY.
- Defect 1 (prefix length): 3-character prefixes (FET, WTR, PSS) always allocate ...000001;
  the second insert fails with `sqlite3.IntegrityError` (reproduced in-memory; documented at
  `docs/KNOWN_LIMITATIONS.md:3-6`). Applies to `feedback_engagement_traces`,
  `within_task_response_candidates`, `practice_state_snapshots`.
- Defect 2 (race): MAX+1 is not concurrency-safe for any table; two overlapping inserts can
  allocate the same id and one fails. Low exposure in the current single-writer local app.
- Present impact: PT/EX/EA/PE (2-char prefixes) are the only production-written tables; target,
  exercise, attempt, and evaluation IDs are safe today. FET/WTR/PSS writes exist only in
  `scripts/demo_journey.py` and tests (single-row fixtures), so the bug is latent for
  production. v0.9.7-B impact: if the loop writes engagement traces (FET) or WTR candidates in
  production, the allocator must be fixed first (SUBSTR prefix length + deterministic
  allocation); if v0.9.7-B writes only targets/exercises/attempts/evaluations, the PT/EX/EA/PE
  path is safe and the fix can be scoped to a dedicated persistence repair (B-REQUIRED, small).

## 11. Confirmed gaps

- G1: No production path maps a persisted Feedback priority to a Practice target (the only
  auto-creation is the demo script; the API ignores priority provenance).
- G2: Target creation endpoint has no learner/source ownership validation and no idempotency;
  duplicate targets are possible.
- G3: Priority provenance is not persisted through the API (source_priority_id/evidence_ids
  dropped by the router).
- G4: Category-to-target-code translation exists only in the demo script (TARGET_CODE_MAP,
  `scripts/demo_journey.py:13-16`); production target creation accepts arbitrary codes, and
  gate categories such as `lexical_repetition` / `connective_use` are not exercise-supported
  without translation.
- G5: Practice page shows no priority context (objective/explanation/revision direction) for a
  target; exercise source text must be pasted manually instead of being seeded from the
  priority evidence quote.
- G6: Attempt submission has no repeated-click protection and no ownership verification;
  cross-student attempts are possible via direct API use.
- G7: No persisted completion semantics; target status never transitions; no finish/continue
  actions; multiple existing targets are unreachable after the first.
- G8: `_next_practice_id` 3-char-prefix defect (FET/WTR/PSS) and MAX+1 race.
- G9: Malformed target_json rows crash the read path (no graceful degradation).
- G10: Exercise-instance creation is not API-idempotent (UI guards, API does not).

## 12. Finding classifications

- B-BLOCKER:
  - Cross-student association via unguarded `POST /api/v1/practice-targets` and
    `POST /api/v1/exercises/{id}/attempts` (payload student_id not verified against the source/
    exercise owner) - must be closed before implementation writes production data.
  - `_next_practice_id` 3-char-prefix defect for any FET/WTR/PSS production write planned in
    v0.9.7-B (currently latent; PT path safe).
- B-REQUIRED:
  - Priority->target mapping service (source: persisted feedback item; translation
    category->target_code; label; evidence; provenance fields persisted).
  - Router forwarding of source_priority_id + evidence_ids with ownership validation.
  - Idempotent target creation (one active target per priority reference; lookup-before-create;
    recommended additive partial unique index).
  - Attempt ownership validation + repeated-click protection (pending guard / idempotency).
  - Persisted completion semantics (terminal per priority reference; status transition or
    equivalent) + explicit completion UI with finish/continue actions.
  - Exercise source-text seeding from the priority evidence quote (and safe fallback to manual
    paste).
  - Safe re-entry and stale/malformed-data degradation.
  - Journey projection verification with priority-derived targets (no code change expected).
- B-OPTIONAL:
  - Engagement-trace (FET) writes for the loop; exercise-instance API idempotency; multi-target
    selection UI; richer evaluation signals for non-lexical codes; allocator repair as part of
    the same phase (recommended).
- DEFER-C: target-completed Journey event/state extension; Journey redesign; WTR/transfer
  pipeline automation.
- DEFER-D/E: Practice page visual consolidation; mobile/accessibility refinements beyond the
  established matrix.
- LATER: mastery/adaptive models; LLM exercise generation; large exercise banks; CEFR or
  proficiency estimation.
- NOT-A-DEFECT: accurate no-target messaging; deterministic oldest-active selection (single
  active target is the v0.9.7-B product rule); INVALID_INPUT attempts not persisted;
  best-effort evaluation with explicit unavailable state; deterministic rule-based evaluation
  without mastery claims; demo-only WTR writes; unsupported target codes returning
  practice_not_available.

## 14. Feasibility of Priority-to-Practice mapping

- Directly mapable: learner ID (essay.student_id), source submission ID (essay_id),
  source diagnosis ID (FeedbackItem.diagnosis_id), category (FeedbackItem.category), explanation
  (FeedbackItem.explanation), evidence quote (FeedbackItem.evidence_quote - seeds exercise
  source text), revision guidance (FeedbackItem.revision_guidance - carries into target/
  exercise display), feedback record (feedback_id from the submission bundle).
- Requires transformation: category -> target_code via a production copy of the demo map
  (`lexical_repetition -> lexical_repetition_local`, `connective_use -> connective_overuse`,
  `sentence_length_pattern -> long_sentence`); unmapped categories must degrade to
  "no exercise available" rather than fabricate a task.
- Missing provenance today: a stable persisted priority reference. The feedback_records JSON
  stores `priority_feedback` lists without per-item ids; the minimal stable reference is the
  tuple (feedback_id, priority index) or a derived `PRIO-{feedback_id}-{index}`; the existing
  `source_priority_id` field can carry it. Prompt/feedback version is available on the feedback
  record (`prompt_version`, `schema_version`).
- Schema change: NOT required for the mapping itself (target_json + source_priority_id already
  exist); a minimal additive partial unique index (migration 13) is recommended to make the
  one-active-target rule database-enforced; otherwise service-level lookup-before-create is the
  minimum.
- Session-only would be unsafe: target creation must persist; session state may carry only the
  selection reference (mirroring v0.9.7-A revision presets).
- Existing rows: remain compatible; legacy rows keep their non-canonical provenance values.
