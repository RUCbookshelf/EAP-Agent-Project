## Objective

Behavior-preserving persistence dependency refactor: remove the broad, untyped
`repository` parameter from `AdminReanalysisService` and replace it with three
exact consumer-owned structural Ports (`AdminConfigurationReadPort`,
`AdminSubmissionReadPort`, `AdminAnalysisPort`), retaining the existing
required keyword-only `revision_repository: RevisionRepository` dependency
introduced by F6A. All six direct persistence calls route to approved owners;
the `ConfigurationService`, `SubmissionService`, and embedded `RevisionService`
collaborations and all preview/run/failure/partial-commit semantics stay
unchanged.

## 3. Exact three Port signatures

Defined in `app/services/admin_reanalysis.py` with `typing.Protocol` +
`@runtime_checkable` (structural satisfaction checks are used by tests),
mirroring the F5A/F5B port pattern. Signatures taken from current HEAD source:

```python
@runtime_checkable
class AdminConfigurationReadPort(Protocol):
    def get_configuration(self, configuration_id_or_version: str) -> ConfigurationVersion | None: ...


@runtime_checkable
class AdminSubmissionReadPort(Protocol):
    def get_submission_bundle(self, essay_id: int) -> dict[str, Any] | None: ...
    def list_student_submissions(self, student_id: str) -> list[dict[str, Any]]: ...


@runtime_checkable
class AdminAnalysisPort(Protocol):
    def get_analysis_run(self, analysis_run_id: str) -> dict[str, Any] | None: ...
    def save_analysis_run(self, essay_id: int, analysis: AnalysisResult) -> AnalysisResult: ...
```

Concrete satisfiers: `SQLiteConfigurationRepository`,
`SQLiteSubmissionRepository`, `SQLiteAnalysisRepository`. No Revision method
appears in the three new Ports; no broad Protocol inheritance; no concrete
SQLite or `Database` import in the Service module.

## 4. Retained RevisionRepository decision

The central `RevisionRepository` is retained unchanged (F6A0/F6A result). It
continues to (a) serve the direct `get_revision_group` read and (b) back the
embedded `RevisionService`. No second Revision argument is introduced; no new
one-method Revision Port is created.

## 5. Constructor before and after

Before:

```python
def __init__(self, repository, settings: Settings, configurations: ConfigurationService,
             submission_service: SubmissionService, *,
             revision_repository: RevisionRepository) -> None:
    self.repository = repository
    self.settings = settings
    self.configurations = configurations
    self.submission_service = submission_service
    self.revisions = RevisionService(revision_repository)
```

After:

```python
def __init__(
    self,
    settings: Settings,
    configuration_reader: AdminConfigurationReadPort,
    submission_reader: AdminSubmissionReadPort,
    analysis_repository: AdminAnalysisPort,
    configurations: ConfigurationService,
    submission_service: SubmissionService,
    *,
    revision_repository: RevisionRepository,
) -> None:
    self.configuration_reader = configuration_reader
    self.submission_reader = submission_reader
    self.analysis_repository = analysis_repository
    self.settings = settings
    self.configurations = configurations
    self.submission_service = submission_service
    self.revision_repository = revision_repository
    self.revisions = RevisionService(revision_repository)
```

`revision_repository` remains required and keyword-only. No broad `repository`
parameter or `self.repository`/`self.repo` field remains. No fallback,
`hasattr`, dynamic discovery, concrete implementation check, `Database`
import, or SQLite import is added.

## 7. Exact preview and run call sequences (current HEAD)

Preview (`preview`, zero-write):

1. `_scope(request)`:
   - submission scope -> `get_submission_bundle`
   - student scope -> `list_student_submissions`
   - revision_group scope -> `get_revision_group`
   - analysis_run scope -> `get_analysis_run`
2. `configurations.active()` (when `configuration_version is None`) or
   `get_configuration(request.configuration_version)`
3. `build_analyzer(...)` + `analyzer.registry.get(analyzer_id)`

Run (`run`):

1. `preview(request)` (re-reads scope and configuration; read-only)
2. `get_configuration(preview["configuration_id"])`; raises `ValueError` if
   `validation_status != "passed"`
3. `build_analyzer(...).registry.get(preview["analyzer_id"])`
4. Per `essay_id` in `preview["submission_ids"]` (in order):
   - `get_submission_bundle(essay_id)` (read)
   - `analyzer.analyze(...)` (no persistence)
   - `save_analysis_run(essay_id, analysis)` (WRITE boundary)
   - if `request.call_llm`: `submission_service.regenerate_feedback(essay_id, saved)`
     (WRITE-capable collaborator)
5. Per `essay_id`: `get_submission_bundle(essay_id).get("revision_group_id")`
   (read); unique non-None group ids
6. Per group id (sorted): `revisions.group(group_id)` (read) then
   `revisions.recalculate(group_id, source_id, target_id)` (WRITE boundary;
   internally the three-sequential-commit Revision workflow:
   `create_revision_group` -> `link_revision` -> `save_revision_snapshot`)

## 8. Six method-to-owner mappings

```text
get_configuration        -> AdminConfigurationReadPort (SQLiteConfigurationRepository)
get_submission_bundle    -> AdminSubmissionReadPort   (SQLiteSubmissionRepository)
list_student_submissions -> AdminSubmissionReadPort   (SQLiteSubmissionRepository)
get_analysis_run         -> AdminAnalysisPort         (SQLiteAnalysisRepository)
save_analysis_run        -> AdminAnalysisPort         (SQLiteAnalysisRepository)
get_revision_group       -> RevisionRepository        (SQLiteRevisionRepository)
```

No seventh direct persistence method exists (verified against
`app/services/admin_reanalysis.py` lines 44-130: exactly these six, no dynamic
method names). `save_analysis_run` is the only direct Analysis write; Revision
writes occur only through the embedded `RevisionService`; feedback persistence
occurs only through `SubmissionService.regenerate_feedback`.

## 9. Service collaborator boundaries

- `configurations.active()` - ConfigurationService, unchanged
- `submission_service.regenerate_feedback(...)` - SubmissionService, unchanged
- `revisions.group(...)` / `revisions.recalculate(...)` - embedded
  RevisionService backed by the exact injected `revision_repository`, unchanged

No Service collaborator call is replaced by a direct repository call; no
Service logic is duplicated or inlined.

## 10. Write and partial-commit boundaries

`AdminReanalysisService` remains an orchestrator over independently committing
operations. No shared transaction, Unit of Work, compensation, rollback, or
retry is added; no earlier successful rows are deleted after a later failure;
exceptions that currently propagate continue to propagate; a downstream
operation never begins after a failure that currently stops the run. The
preview path performs zero writes. Revision write methods and transaction
boundaries are untouched.

## 11. Failure-semantics matrix

1. Failure before `save_analysis_run` (e.g. missing bundle, missing
   configuration, unvalidated configuration, analyzer failure): zero Analysis
   writes; zero later write-capable collaborator calls.
2. Failure in `save_analysis_run`: exception propagates; no Revision or
   feedback-regeneration call begins for that or later essays.
3. Failure after a successful `save_analysis_run` (feedback regeneration
   failure): the committed Analysis Run remains visible; no compensation.
4. Failure in the Revision collaborator after Analysis persistence: committed
   Analysis runs remain visible; Revision commits completed internally remain
   (F6A three-sequential-commit behavior, unchanged); exception propagates.
5. Failure in optional feedback regeneration: earlier Analysis (and any
   earlier feedback) commits remain; exception propagates; no later
   operation begins.
6. `call_llm=False`: exactly zero `regenerate_feedback` calls.

## 15. Rollback plan

If a focused check fails, identify the smallest affected Port/branch/seam,
reproduce with one focused test, compare against the Phase 0 call-order and
failure matrix, repair only that component, rerun focused checks, and only
then run the full suite. If completion requires any repository/SQL/transaction/
Protocol/Service behavior/facade/API change, stop and create
`docs/development/BLOCKER_REPORT_V0.9.5_F6B.md`; no broad fallback or scope
expansion.

## 16. Stop conditions

Stop and create the blocker report if completion requires: changing a

behavior, the `Database` constructor or public surface, API paths/schemas,
