# v0.9.5-F3 — Learner Read-Model Dependency Narrowing

## Scope

Included: `ProgressService`, `LearnerProfileService`, `DashboardService`, their
composition in `build_submission_service`, `_run_startup`, `_build_full_app`,
and the explicitly authorized `FeedbackPipeline` composition exception.

Excluded: every other Service, router, repository implementation, facade
method, SQL/DDL/migration, transaction, schema, domain model, frontend, locale,
and UI concern. F4/F5/G remain deferred.

## Dependency change

Current:

```text
DashboardService(Database) ─┐
LearnerProfileService(Database) ─┼─> ProgressService(Database)
                                  └─> hasattr capability discovery
```

Target:

```text
SQLiteLearnerRepository ─> DashboardService ─> ProgressService
SQLiteLearnerRepository ─> LearnerProfileService ─> ProgressService
SQLiteLearnerRepository ─> ProgressService
SQLiteConfigurationRepository ─> ProgressService
```

The existing `Database` instance remains the owner of both extracted repository
instances. Separate ProgressService instances retain the existing service
lifetime pattern.

## Consumer-owned Ports

```python
class DashboardReadPort(Protocol):
    def list_visualization_records(self, student_id: str) -> list[dict[str, Any]]: ...

class LearnerProfileReadPort(Protocol):
    def get_latest_learner_profile(self, student_id: str) -> dict[str, Any] | None: ...
    def list_learner_profile_snapshots(self, student_id: str) -> list[dict[str, Any]]: ...

class LearnerProgressPort(Protocol):
    def list_visualization_records(self, student_id: str) -> list[dict[str, Any]]: ...
    def save_learner_profile_snapshot(self, snapshot: LearnerProfileSnapshot) -> LearnerProfileSnapshot: ...

class ActiveConfigurationPort(Protocol):
    def get_active_configuration(self) -> ConfigurationVersion: ...
```

No Port declares a method its consumer does not call.

## Constructors and composition

- `ProgressService(learner_repository, configuration_repository, rules=RULES)`
- `LearnerProfileService(repository, progress_service)`
- `DashboardService(repository, metrics, progress_service)`
- `build_submission_service` accepts optional keyword-only Learner and
  Configuration composition inputs. Production supplies extracted instances;
  legacy callers use the existing repository argument for both explicit Ports.
- Both application construction paths and `FeedbackPipeline` reuse their
  facade-owned `_learner_repository` and `_configuration_repository` objects.

`ProgressService` directly calls `list_visualization_records`,
`get_active_configuration`, and (when `persist=True`)
`save_learner_profile_snapshot`. Its inactive `list_longitudinal_records`
fallback and the relevant `hasattr` discovery branches are removed only from
this chain. Existing facade/repository methods remain untouched.

## Behavior preservation

- `persist=False`: zero snapshot/evidence writes.
- `persist=True`: exactly one repository snapshot save; repository transaction
  ownership is unchanged.
- Active configuration is queried once at the same calculation point; missing
  configuration preserves the existing default payload/version behavior.
- Learner Profile reads, recalculation, ordering, shapes, and errors are
  unchanged.
- Dashboard direct reads, `persist=False` snapshot creation, output shape,
  labels, ordering, empty state, and zero-write behavior are unchanged.
- Submission and FeedbackPipeline public constructors, workflows, call order,
  persistence, transactions, providers, exceptions, and returns are unchanged.
