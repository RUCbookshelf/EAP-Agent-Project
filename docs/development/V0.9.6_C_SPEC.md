## C1 - No-priority workflow completion

### Incident (Submission #28, learner S02)

The no-priority Diagnostic Gate result was a navigation dead end: Writing
kept its stale "Writing submitted" completion panel, Feedback offered no
action for the no-priority result, Revision and Practice had no meaningful
next step, and Home always presented Writing as the only current action.
The user looped Writing -> Feedback -> Writing unchanged.

### Cause (source-proven)

The Writing success panel is session state (`submission_result` +
`_writing_saved_for_learner`) with no terminal action to clear it; the
no-priority Feedback branch had no actions; and Home's current-step
derivation had no acknowledgement for a finished no-priority cycle, so the
only presented action remained "Write".

### Fix (accepted C1 commits `c7c7222`, `41ad11f`)

- Feedback no-priority branch shows one no-priority heading, exactly one
  `Suggested Next Step`, the neutral `Passage From Your Writing` section
  (never an unsupported Strength), the submission reference, and two
  explicit controls:
  - `Revise This Draft` - enters the existing revision-writing mode with the
    current submission preserved as the source; no automatic priority is
    fabricated and no Practice target is created to enable navigation.
  - `Finish This Feedback Cycle` - `_finish_feedback_cycle` records the
    session acknowledgement (`no_priority_reviewed` = exact submission id,
    `cycle_finished_notice`), clears the stale Writing-submitted panel, and
    returns Home/Writing to a fresh `1 Write` state.
- Home derivation: while the latest no-priority result is unresolved, Home
  shows `Latest submission / Feedback result: No automatic priority
  selected / Next action: review and choose`; after the exact finished
  submission is acknowledged, Home returns to `1 Write`.
- Revision and Practice explain the absent automatic focus/target and stay
  actionable; Practice may legitimately be skipped for the cycle.
- Locale: 12 new en/zh keys (parity 528 -> 540/540).

## C2 - Native Streamlit icon rendering repair

### Root cause (rendered-DOM proven)

1. Sidebar: the pixel-art rule
   `div[data-testid="stSidebar"] * { font-family: var(--px-font-body)
   !important; }` applied the pixel font to every sidebar element, so the
   native collapse/expand icon spans lost the Material Symbols Rounded font
   and their ligatures rendered as literal `keyboard_double_arrow_*` text;
   Streamlit's stock hover-only visibility also hid the collapse control
   until hover.
2. Writing Genre area: the same defect class - the base typography rule
   `.stApp p, ..., .stApp span, ...` (specificity 0,1,1) overrode
   Streamlit's icon-class rule for the two expander chevrons
   (`span[data-testid="stIconMaterial"]` with ligature
   `keyboard_arrow_right` inside the Timing and Tools Used expanders),
   rendering overlapping literal ligature text. The Genre selectbox was
   unaffected (SVG arrow, no ligature span).

### Fix (accepted C2 commits `d2c28fe`, `2e34d58`, `df84f71`)

- Narrowed the sidebar text rule to exclude native button content and
  restored the Material Symbols font + `liga` on the two documented native
  controls (`stSidebarCollapseButton`, `stExpandSidebarButton`); pinned the
  two native controls `visibility: visible` so arrows show before hover.
- Common base-rule correction: `.stApp span:not([data-testid=
  "stIconMaterial"])` excludes every Streamlit native icon span from the
  pixel body-font rule, restoring the distribution-owned Material Symbols
  rule for the sidebar icons and both Genre expander chevrons.
- No per-control patches, no hiding tricks, no pseudo-element arrows, no
  replacement controls, no unbounded `!important`.
