## 2. Journey projection architecture (reconstructed, MCU 6.1)

The Journey is a **read-time derivation** (`app/journey/service.py:1-19`):
`JourneyService.get_journey(student_id)` reads eight learner-scoped record
sets through `JourneyProjectionReadPort` (service.py:112-121), derives
events, classifies state, and returns counts/events/states. The service
contains no write path; repeated reads are side-effect free
(service.py:126-135, 428+; verified by `test_journey_v093c.py`
`test_get_journey_is_read_only` / `test_no_engagement_trace_written`).

Record sources and their events:

| Persisted record | Event type | Deduplication key |
|---|---|---|
| essay (no `revision_of_submission_id`) | `writing_submitted` | `writing_submitted:essay:{essay_id}` |
| essay (with `revision_of_submission_id`) | `revision_submitted` | `revision_submitted:essay:{essay_id}` |
| analysis_run | `analysis_completed` | `analysis_completed:analysis_run:{analysis_run_id}` |
| essay without analysis run | `insufficient_evidence` (derived) | `insufficient_evidence:essay:{essay_id}` |
| feedback_record | `feedback_available` | `feedback_available:feedback_record:{feedback_id}` |
| feedback_record with `priority_feedback` count > 0 | `feedback_priority_available` | `feedback_priority_available:feedback_record:{feedback_id}` |
| feedback_record with zero priorities | `feedback_without_priority` (derived) | `feedback_without_priority:feedback_record:{feedback_id}` |
| practice_target | `practice_available` | `practice_available:practice_target:{practice_target_id}` |
| exercise_attempt | `exercise_attempted` | `exercise_attempted:exercise_attempt:{attempt_id}` |
| practice_evaluation | `practice_evaluation_recorded` | `practice_evaluation_recorded:practice_evaluation:{evaluation_id}` |
| within_task_response_candidate | `within_task_response_observed` | `within_task_response_observed:within_task_response_candidate:{response_id}` |
| transfer_evidence_candidate | `later_task_evidence` | `later_task_evidence:transfer_evidence_candidate:{transfer_evidence_id}` |

Each event carries `source_record_type`, `source_record_id`, `learner_id`,
`task_id`/`submission_id`, `occurred_at`, `event_version`
(`journey-event-v0.9.3-c`), conservative `limitations`, and `research_detail`.
The `practice_available` event carries `research_detail.status` from the
persisted target status (service.py:294-310); the completed status therefore
flows through as `status: "completed"` **without any new event type**.
The `exercise_attempted` event carries `research_detail.status` from the
attempt (`submitted`); `practice_evaluation_recorded` carries
`completion_status`/`target_action_status` from the evaluation payload.

## 3. Ordering rule (service.py:414-430)

Events sort by `(essay_submitted_at.get(submission_id, occurred_at),
EVENT_STAGE_ORDER.get(event_type, 50), source_record_id, event_type)`.
Essay-anchored events use the essay's submitted timestamp; practice
attempt/evaluation events (no submission_id) use their own `occurred_at`.
The secondary stage order is `writing/revision=10, insufficient=20,
analysis=30, feedback=40, priority=50, practice_available=60,
exercise_attempted=70, evaluation=80, WTR=90, later=100`. The tie-breakers
(stage, source id, type) are deterministic for identical persisted data.

## 4. Expected projection for one complete priority-derived cycle

Persisted records (product path, one explicit action each): 2 essays
(original + linked revision), 2 analysis runs, 2 feedback records (the
original produces the priority-bearing feedback; the revision submission
runs the same production pipeline and produces its own analysis + feedback
record, which with the deterministic local fixture carries no priority), 1
priority-derived practice target, 1 exercise instance, 1 exercise attempt,
0 or 1 practice evaluation (controlled scenario), no WTR/transfer rows
(those tables are demo/test-only on this path), no Journey persistence
rows (Journey is read-time). Empirically verified through the production
API on an isolated database (2026-08-05 probe; pinned by the WU6 focused
suite).

Expected Journey events:

- Evaluation-available scenario: `writing_submitted`,
  `analysis_completed`, `feedback_available`,
  `feedback_priority_available`, `practice_available`,
  `exercise_attempted`, `practice_evaluation_recorded`,
  `revision_submitted`, `analysis_completed` (revision),
  `feedback_available` (revision), `feedback_without_priority` (revision)
  = **11 events** for the deterministic two-essay cycle.
- Evaluation-unavailable scenario: the same minus
  `practice_evaluation_recorded` = **10 events**.
- Whether the revision's own feedback record yields
  `feedback_priority_available` or `feedback_without_priority` depends on
  the deterministic local content; the test fixture and the browser matrix
  record the exact observed set instead of assuming it.
- Target completion creates **no event**; the `practice_available` event's
  `research_detail.status` changes `active` -> `completed`; event count and
  ordering are unchanged. Journey reads before and after completion return
  the same event keys.
- State classification after attempt+evaluation (no WTR): `revision_no_response`
  (`_classify_state`, service.py:428-481); completion does not change the
  state classification because classification depends on record presence,
  not status.

## 5. Provenance rules

- Every event belongs to the requesting learner: all reads are
  student-scoped (`JourneyProjectionReadPort` signatures; repository SQL
  `WHERE student_id=?` for targets/attempts/evaluations, joins through
  essays for analyses/feedback).
- `practice_available`: `learner_id` = target.student_id; `submission_id`/
  `task_id` = target.source_submission_id; `research_detail` carries only
  `target_code` + `status` (no fabricated priority provenance).
- `exercise_attempted`: `learner_id` = attempt.student_id; `task_id` =
  attempt.exercise_id.
- `practice_evaluation_recorded`: joined through the attempt's student
  (`list_practice_evaluations_by_student`, practice.py:222-232), so a
  learner never sees another learner's evaluation.
- Event labels never overstate outcomes (fixed limitation strings; no
  mastery/proficiency/CEFR/learning-gain wording).

## 6. Evaluation-unavailable semantics

- A persisted attempt with no valid evaluation row projects
  `exercise_attempted` only; **no** `practice_evaluation_recorded` event is
  fabricated, and no failure/mastery implication is derived
  (service.py:312-329).
- WU5 evaluation read semantics stay authoritative: AVAILABLE /
  UNAVAILABLE / MALFORMED (malformed rows degrade to controlled
  unavailable; `app/practice/evaluations.py`).

## 7. Legacy target semantics

- A legacy target (no priority provenance) projects `practice_available`
  with its stored `target_code`/`status`; no priority provenance is
  fabricated. A legacy target with a valid attempt and optional completion
  projects exactly the same event set as any other target
  (service.py:294-310; WU5 protocol section 11).

## 8. Malformed-row contract on the verified path

- Records created by the verified WU2-WU5 product path are schema-validated
  and well-formed by construction (Pydantic `extra="forbid"` models; JSON
  written by the repositories).
- Malformed evaluation rows on the verified path degrade to controlled
  unavailable in the WU5 evaluation read service (never a page crash).
- The pre-existing repository-wide malformed-`*_json` read crash (audit G9,
  `docs/KNOWN_LIMITATIONS.md`) is NOT on the verified path and is out of
  WU6 scope (repository-wide repair is deferred); WU6 tests verify that no
  valid WU2-WU5 record shape crashes Journey and that malformed evaluation
  rows never fabricate events or cross-associate learners.

## 9. Release-blocker definition (only this permits production changes)

A reproducible defect that: prevents accurate Journey projection for valid
WU2-WU5 records; corrupts learner/source ownership or provenance;
duplicates targets/exercises/attempts/evaluations/Journey events; breaks
the final product path; causes a verified UI failure; causes Journey reads
to write; or prevents release closure. Fixes require a failing test first,
the smallest production change, learner/provenance/dedup/legacy tests, and
a focused commit. A new Journey event type, migration 14, or broad
projector rewrite is a stop-and-report condition, not a permitted fix.

## 10. Final product-matrix scenarios (MCU 6.3)

Four independent combinations (en/zh_CN x 1280x900/390x844), each with a
fresh isolated database, a distinct learner, local provider only, no
shared browser/session state, and independently recorded evidence:

1. Main scenario: learner -> first writing -> structured feedback ->
   persisted priority -> priority-guided revision -> linked revision ->
   explicit revision completion -> Open Practice -> create-or-reuse target
   -> persisted priority context -> reuse/create one exercise -> verify
   priority/rationale/evidence/direction/instruction -> empty response
   (zero writes) -> valid response -> one persisted attempt -> evaluation
   or honest unavailable -> Finish This Practice Cycle -> target COMPLETED
   -> reload/re-entry recovery -> Feedback re-entry -> Revision re-entry ->
   Open Learning Journey -> verify the complete existing projection.
2. Evaluation-unavailable scenario (one justified focused matrix per
   locale): valid persisted attempt, evaluation unavailable through the
   supported mechanism, completion succeeds, Journey stays truthful.
3. Multiple-target scenario: one completed target + one other active
   target; normal entry prefers active; explicit re-entry shows completed;
   other target opens only explicitly; no automatic generation/ranking.
4. No-priority scenario: no fabricated priority, no automatic target, no
   broken Revision/Practice pages.
5. Legacy target scenario: no priority provenance, valid attempt, optional
   completion, readable Journey without fabricated provenance.

Persisted source-scoped counts (main learner): at most one target per
priority key, one current exercise, one attempt per explicit submit, zero
or one evaluation, one completed target row, zero new Journey persistence
rows, zero uncontrolled duplicates after all re-entry checks.
