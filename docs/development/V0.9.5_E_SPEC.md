**Baseline:** `769e6d8` (v0.9.5-D verification)<br>

## 1. Public `Database` compatibility surface

`Database` and `SQLiteRepository = Database` remain importable from both
`app.database` and `app.database.repository`. The baseline has exactly **86**
public methods: 55 reads, 27 direct writes, three infrastructure/write-capable
methods, and one pure compatibility helper. Names, signatures, defaults,
positional/keyword behavior, return values, exception behavior, SQL meaning,
ordering, connection scopes, commits, rollbacks, and call sites are frozen.

The complete per-method signature, source line, SQL fingerprint, direct table
access, call-site, Protocol, transaction, and return-annotation inventory is the
machine-readable baseline named above.

## 4. Cross-aggregate reads and compositions

The existing owner retains each use-case query or composition:

- System: `counts` (operational projection across the historical count set).
- Submission: `prior_records`, `get_submission_bundle`.
- CALF: `list_analysis_units`, and the essay-existence guard inside
  `save_error_annotations`.
- Learner: `get_student`, `list_all_students`, `list_longitudinal_records`,
  `list_visualization_records`.
- Revision: `create_revision_group`, `link_revision`, `get_revision_group`,
  `get_revision_group_for_submission`, `list_revision_candidates`.
- Practice/Journey projection: `list_essays_by_student`,
  `list_analysis_runs_for_student`, `list_feedback_records_for_student`.

The original SQL and separate-connection behavior remain intact. SQL is not
duplicated between repositories. A child repository never imports the facade.

## 5. Connection and transaction ownership

`SQLiteConnectionManager` owns only the current low-level behavior:

- `Path` storage and parent-directory creation;
- `sqlite3.connect(..., factory=ClosingConnection)`;
- `sqlite3.Row` row factory;
- `PRAGMA foreign_keys = ON`;
- current context-manager commit/rollback/close behavior;
- the explicit `BEGIN` → yield → commit / rollback-and-reraise → close
  transaction context.

No pool, retry, async wrapper, global connection, thread change, hidden read
commit, or automatic per-repository migration is introduced. All aggregate
repositories receive the same manager instance. Existing multi-connection
methods and pre-read/write/post-read boundaries remain multi-connection; in
particular, Practice and Research ID allocation remains separate from insert.

No generic business-SQL `common`, `all`, `helpers`, or `utils` repository is
allowed. `SCHEMA` remains in `repository.py` because Migration 1 imports it;
DDL consolidation is explicitly deferred.

## 7. Facade construction and delegation

`Database(path)` constructs one `SQLiteConnectionManager`, then explicitly
constructs the nine repositories above with that manager. Every current public
method remains explicitly declared on `Database` and delegates to exactly one
approved owner; unrestricted `__getattr__` is prohibited. Infrastructure-level
compatibility methods may delegate to the manager through `SystemRepository`.
Services, routers, factories, scripts, and tests continue to receive the same
facade. Existing constructor annotations and repository Protocol method sets do
not change.

## 8. SQL, result, and transaction parity

- Pre/post public method sets and `inspect.signature` values must be identical.
- SQL fingerprints normalize whitespace only; statement order, placeholders,
  selected columns, joins, predicates, conflict clauses, ordering, and batch
  cardinality must not drift.
- Connection count and boundaries, implicit context-manager commits/rollbacks,
  explicit transaction events, write counts, result ordering, JSON/bool/model
  reconstruction, exceptions, and messages remain identical.
- `Migration 12`, the 33-table set, columns, defaults, indexes, foreign keys,
  constraints, and schema fingerprint must match the fresh pre-change snapshot
  exactly.

## 9. Fresh-database verification policy

Every write-capable test or smoke run must clear `DATABASE_URL`, set
`DATABASE_PATH` to a newly created temporary directory, force
`LLM_PROVIDER=local`, print and assert the effective/opened database path,
initialize Migration 12, verify expected seeded/empty state, close connections,
and remove the temporary database. It must assert that the path is neither
`data/writing_feedback.db`, the v0.9.5-B backup, nor any `.env` database.

The development database is never opened for write and is checked only by
size, modification time, and SHA-256 before/after verification. Historical
records, row IDs, row counts, backups, upgrade compatibility, conversion, and
rollback migration are not acceptance inputs.

## 10. Allowed files

Production changes are limited to `app/database/repository.py`, new modules
under `app/infrastructure/sqlite/repositories/`, and minimal exports in
`app/database/__init__.py` / `app/infrastructure/__init__.py`. Test changes are
limited to connection/transaction, aggregate repository, facade parity,
ownership/dependency, and isolated fresh-database integration coverage.
Evidence stays under `verification/v0.9.5-e/`. Documentation changes are
limited to the files approved by the stage goal.

## 11. Explicit non-goals and deferred findings

No Service dependency narrowing, Protocol consolidation, facade contraction,
public method removal, schema cleanup, Migration 13, DDL move, ORM/SQLAlchemy,
pooling, async persistence, Unit of Work, DI framework, SQL rewrite, API/client
change, domain change, UI change, version-constant fix, WTR collision fix,
`export_jobs` writer, legacy `FeedbackPipeline` removal, endpoint/client cleanup,
test-pyramid rebalance, historical-data migration, or user-owned-file change.

Duplicated/incomplete Protocols, the WTR allocation collision, version drift,
the unimplemented export writer, legacy pipeline, and unused API/client surface
remain recorded and deferred.

## 12. Rollback plan

The implementation is one isolated commit. Rollback is `git revert` of that
commit on a clean task-owned diff, followed by the focused repository/Service
suite and fresh-schema comparison. Existing data is not a rollback fixture.
If parity requires a schema, SQL, transaction, public-facade, Service
constructor, ORM, async, historical-data, or UI change, stop and create
`docs/development/BLOCKER_REPORT_V0.9.5_E.md` instead.
