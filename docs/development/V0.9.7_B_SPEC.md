## 1. Primary goal

Complete the learning loop from a persisted Feedback priority to a focused, persisted,
evaluated, and safely completable Practice cycle:

```text
Persisted Feedback Priority
→ one traceable Practice Target
→ Focused Practice task (target + source evidence + objective + instructions)
→ Student Practice attempt (validated, persisted)
→ Bounded rule-based evaluation (no mastery/learning claims)
→ Explicit completion state and next step
→ Safe re-entry and reuse rules
```

Preserve the completed v0.9.7-A Feedback -> Revision behavior as a frozen baseline. Do not
generate more feedback; do not change the Feedback schema.

## 3. Frozen target workflow

```text
Feedback page (priority exists)
→ student selects/confirms the priority (v0.9.7-A semantics; persisted source feedback is authoritative)
→ Priority-to-Practice transfer action (Open Practice with target intent, or automatic on entry)
→ Idempotent target resolution: lookup existing target for (student, source submission, priority reference)
   → existing ACTIVE target: reuse (no duplicate)
   → existing COMPLETED target: show its saved result (no new target)
   → none: create one ACTIVE target with full provenance
→ Practice page renders the focused task (target label, objective, evidence, instructions, source text seeded)
→ Student submits one attempt (validated, persisted, repeated-click protected)
→ Rule-based evaluation persisted (or explicit unavailable state)
→ Explicit completion state (target terminal per priority reference) with next steps
→ Re-entry shows the existing result; no blank/duplicate form
→ Home/Journey reflect the target/attempt/evaluation records (existing projection)
```

## 4. Priority-to-Practice mapping contract

- Authoritative source: the persisted source submission bundle
  (`feedback_records.feedback_json.priority_feedback[selected_index]`) - never rendered page
  text, never an unverified session copy. Session state may carry only the reference
  (`source_submission_id`, `feedback_id`, `priority_index`), revalidated on every render.
- Inputs: student_id, source_submission_id, feedback_id, priority index, FeedbackItem fields
  (diagnosis_id, category, evidence_quote, explanation, revision_guidance), prompt/schema
  version from the feedback record.
- Mapping rules:
  - target_code = production copy of the demo map
    (`lexical_repetition -> lexical_repetition_local`, `connective_use -> connective_overuse`,
    `sentence_length_pattern -> long_sentence`); unmapped categories produce NO target and an
    accurate "no practice available for this priority" state (never a fabricated task).
  - target_label = localized learner-facing category label (existing
    `student_feedback_category_*` labels).
  - evidence_ids = [feedback_id reference] (plus any persisted evidence reference available).
  - exercise source_text = priority `evidence_quote` when present; manual paste remains the
    fallback.
  - revision_guidance + explanation are carried into the target/task display fields (stored in
    `target_json`; no new Feedback fields).
- Provenance reference: `source_priority_id` = stable string derived from the persisted
  feedback record, e.g. `PRIO-{feedback_id}-{priority_index}`; documented once in the code and
  used for idempotency.

## 5. Provenance model

Every target must persist (in queryable columns and/or `target_json`):

- learner: `student_id`;
- source essay: `source_submission_id`;
- source feedback record: `feedback_id` (via `source_priority_id` reference + stored field);
- source priority: `source_priority_id` (stable reference above) + `priority_index`;
- source diagnosis: `source_diagnosis_id` (FeedbackItem.diagnosis_id);
- creation versions: `diagnostic_version`, `configuration_version` (already defaulted),
  plus the feedback prompt/schema version captured from the feedback record;
- target status: `status` (active/completed lifecycle per section 8).

Existing rows remain untouched and compatible; legacy DEMO rows keep their non-canonical
`PRIO-{essay_id}` references.

## 6. Idempotency contract

- Logical idempotency key: `(student_id, source_submission_id, source_priority_id)`.
- Rule: at most one ACTIVE target per key; at most one target (any status) per key unless the
  priority reference itself changes (a new feedback record/index is a new key).
- Enforcement:
  1. Service-level lookup-before-create (list/get by key) inside the creation service method;
  2. Recommended additive partial unique index (migration 13, additive and non-destructive) on
     `practice_targets(student_id, source_submission_id, source_priority_id)` filtered to
     `status = 'active'` (or a stored computed key column) as database-level protection;
  3. The UI transfer action must never create on render: creation happens only through one
     explicit service/API call triggered by navigation intent, with a pending guard mirroring
     the v0.9.7-A submit guards.
- Repeated clicks, retries, reruns, refreshes, and re-entry return the existing target (200
  with the existing record) instead of inserting a duplicate. Concurrent requests are resolved
  by the unique index (one succeeds, the other returns the existing row).

## 7. Active-target selection and recovery rules

- Selection: the target bound to the transferred priority reference (from Feedback/Revision)
  is authoritative; when the student enters Practice without an explicit reference, the
  existing deterministic rule applies (oldest active target), and the priority-derived target
  is guaranteed reachable because the one-active-target rule keeps the set small.
- Transfer: the Feedback/Revision action carries `{source_submission_id, feedback_id,
  priority_index}` in session state; the Practice page validates it against the persisted
  records before rendering.
- Recovery: rerun revalidates; refresh re-derives from persisted records (lookup by key);
  a stale reference (target deleted, source missing, priority changed) degrades to the
  deterministic no-target/oldest-active behavior with an accurate note.
- Ownership: every resolution is learner-scoped server-side; foreign targets are never
  returned or rendered.

## 8. Attempt and completion semantics

- One explicit submission action per task; empty/invalid input rejected client- and
  server-side (existing minimum: 3 non-blank characters; INVALID_INPUT attempts are not
  persisted).
- Attempt persistence: one `exercise_attempts` row per accepted submission with
  `attempt_number`, timestamps, status SUBMITTED, and the response text; server verifies the
  payload student_id owns the exercise's target (cross-student rejection) before persisting.
- Duplicate prevention: UI pending guard (mirror v0.9.7-A `enter_pending`/`consume_pending`),
  no automatic retry, and saved-state lock; API remains append-capable for legitimate retries
  only when explicitly supported by the UI.
- Evaluation: rule-based (`PracticeService.evaluate_attempt`), persisted as one
  `practice_evaluations` row per attempt, best-effort (attempt authoritative; failure shows an
  explicit "evaluation unavailable" state and never a false success).
- Completion rule (frozen): the priority-reference task is COMPLETE when one SUBMITTED attempt
  exists and either a persisted evaluation exists or the evaluation is explicitly unavailable
  (recorded as such). Completion is terminal for that priority reference: the target transitions
  from ACTIVE to COMPLETED (new enum value in `PracticeTargetStatus`, code-only, column stores
  TEXT so no migration is required), re-entry shows the saved result, and no new target is
  created for the same key.
- Failure handling: submission failure preserves the input (widget state) and shows a
  recoverable error; no false success; no data loss.

## 9. Completion and re-entry semantics

- After completion the Practice page shows: confirmation that the attempt was saved and the
  task is complete, the target label, the evaluation summary (or the explicit unavailable
  notice), conservative limitation wording, and clear next steps:
  - Finish this practice cycle -> Home (safe end; journey-derived next state);
  - Open Learning Journey;
  - (only when another active target exists) open the next existing target.
- Re-entry (refresh, direct navigation, rerun): loads the persisted target/attempt/evaluation
  and shows the completion state; never a blank or duplicate form; never re-creates the target.
- Home/Journey: existing projection already reflects target/attempt/evaluation records;
  verification must confirm `target_no_attempt` -> `attempt_no_evaluation` -> next states.

## 16. Acceptance criteria (candidate, frozen for implementation)

1. A persisted Feedback priority can create or reuse one traceable Practice target.
2. Repeated clicks, retries, reruns, and refreshes do not create duplicate active targets.
3. The target is associated with the correct learner, source essay, source feedback, and
   source priority.
4. Cross-student and cross-source associations are rejected.
5. Practice displays the active target, source evidence, objective, and clear task.
6. A student can submit a valid Practice attempt.
7. The attempt is genuinely persisted.
8. Submission or evaluation failure does not lose the student's input or produce false success.
9. Evaluation remains bounded and does not make unsupported mastery or learning-gain claims.
10. A successful attempt produces an explicit completion state and clear next steps.
11. Re-entry displays the existing target/attempt state rather than an uncontrolled duplicate
    form.
12. Missing, stale, malformed, completed, or unavailable targets degrade safely.
13. Target, attempt, evaluation, and completion are visible to existing Journey projection or
    receive only the minimum necessary integration.
14. Existing Writing, Feedback, Revision, Practice, Journey, and Research baseline behavior is
    not broken.
15. Automated tests and the EN/ZH x desktop/mobile rendered matrix pass independently.
16. `_next_practice_id` collision risk is resolved or proven irrelevant to the production path.
17. User-owned files remain untouched.
18. Final changes pass impact review and provide reproducible evidence.

## 17. Blocking and stop conditions

Stop and report (no silent workaround) if: data loss; security or cross-student association
defect; startup or submission failure; a required migration beyond the additive partial unique
index; a required redesign of Feedback or Practice models; evidence that the loop requires
v0.9.7-C/D/E scope; or regression of v0.9.7-A behavior. Non-blocking findings are recorded as
deferred work.
