## 1. Objective and boundary

Redesign only the six Student pages on Hybrid Pixel System 2.0 so a learner
can identify the page purpose, current task, most important information, next
action, and interpretation limits. Preserve migration 12,
`config-v0.9.0`, domain semantics, API schemas, idempotency, privacy, and the
read-time Journey projection.

This stage does not redesign Research pages and does not begin v0.9.4-C,
v0.9.4-D, v1.0, corpus work, machine learning, provider work, or a real pilot.

## 3. Shared Student structure

The smallest shared presentation layer will be added to
`app/ui/components.py` and the existing canonical CSS generated by
`app/ui/pixel_art.py`:

- a Student page intro marker with localized purpose text and stable
  `data-testid`;
- a compact Student task-step list for Home and Practice;
- a Student action/guidance block for next-action and accurate no-action
  states;
- a compact context/detail block for Home and Revision;
- existing notices, validation, empty states, priority cards, evidence quotes,
  technical captions, and timeline primitives remain authoritative.

The Student page marker activates the existing 720px Student content-width
alias and 32px Student section-density alias. It does not add a CSS injection
entrypoint, token map, local font stack, page-local palette, rounded SaaS card
system, or decorative motion.

Stable selectors will cover page purpose, step state, primary-action region,
learner context, evidence, limitations, and technical metadata. Application-
owned mobile controls remain at least 44×44 CSS pixels.

Exact new selector contract:

- `div[data-testid="stMainBlockContainer"]:has([data-testid="px-student-page"])`
- `[data-testid="px-student-page"]`
- `[data-testid="px-student-steps"]`
- `[data-testid="px-student-primary-action"]`
- `[data-testid="px-student-context"]`

## 4. Frozen page contracts

### 4.1 Home

| Contract item | Frozen decision |
|---|---|
| Purpose | Orient the learner, show active learner context, explain the available workflow, and direct the next relevant action. |
| Current primary action | None; the next action is currently a non-interactive info box. |
| Major issue | Status/count information dominates while the workflow and next action are weak. |
| Minimal redesign | Purpose first; compact learner context; three-step workflow; one state-derived CTA; subordinate status/latest activity; technical detail omitted; limitation retained. |
| Reused components | Student intro, task steps, context block, action block, notices, limitation notice. |
| Acceptance | Missing/valid learner, unavailable API, English desktop, Chinese mobile, focus, touch targets, no overflow/raw keys, and zero render writes. |

Home must not become a metric, proficiency, ranking, or performance dashboard.

### 4.2 Writing

| Contract item | Frozen decision |
|---|---|
| Purpose | Make the prompt/essay hierarchy, requirements, submission state, and single next action clear. |
| Current primary action | Submit Writing. |
| Major issue | The form is long; required state appears only after submission; technical task settings compete with the essay. |
| Minimal redesign | Purpose first; learner and task relationship; visible required prompt and essay fields; field-local validation; optional timing/tools subordinate; one full-width submit; locked success state prevents accidental resubmission; IDs secondary. |
| Reused components | Student intro/action block, field error, loading/success/error notices, feedback renderer. |
| Acceptance | Empty prompt and essay stay local with zero API/write; valid submit produces one request/essay; refresh/locale do not duplicate; classified outage has no false success; long mobile text remains readable. |

The request schema, server validation, request ID, retry, timeout, and
idempotency contracts remain unchanged.

### 4.3 Feedback

| Contract item | Frozen decision |
|---|---|
| Purpose | Put the Diagnostic-Gate-selected priority and learner action first, then supporting evidence and limitations. |
| Current primary action | None; next step is a non-interactive info box. |
| Major issue | Strengths and provider/essay metadata precede the selected priority; evidence/action boundaries are weak. |
| Minimal redesign | Priority or accurate zero-priority state first; suggested action next; evidence linked beneath; strengths secondary; provider and IDs removed from the learner-facing lead; limitation retained; one relevant CTA when action exists. |
| Reused components | Student intro/action block, priority card, evidence quote, empty state, limitation notice, technical caption only where necessary. |
| Acceptance | One-priority, zero-priority S02, learner/result absent, outage, evidence/limitation presence, no fabricated priority, no render/locale trace, English desktop, Chinese mobile. |

Diagnostic Gate results, quotations, priority order, provenance, and
zero-priority semantics are immutable.

### 4.4 Practice

| Contract item | Frozen decision |
|---|---|
| Purpose | Make target → exercise → response → evaluation explicit and emphasize only the current actionable step. |
| Current primary action | Load Practice, followed conditionally by Generate Exercise and Submit Attempt. |
| Major issue | The learner must load read-only state manually; internal target codes dominate; multiple possible actions compete. |
| Minimal redesign | Read targets/instances automatically without writes; show a four-step sequence; expose only the current action; use learner-facing target labels; separate instruction, response, saved attempt, and evaluation; lock the accepted response against duplicate submission. |
| Reused components | Student intro/task steps/action block, notices, validation, limitation notice. |
| Acceptance | No target, active target, instance stays one across refresh, invalid response writes nothing, valid response writes one attempt/evaluation, restart/refresh/locale do not duplicate, English desktop, Chinese mobile. |

No scores, levels, streaks, badges, mastery claims, automatic retry, or changed
practice evaluation semantics are permitted.

### 4.5 Revision

| Contract item | Frozen decision |
|---|---|
| Purpose | Connect the original submission context and feedback target to a revised-text task, then separate conservative observation from learner claims. |
| Current primary action | None; the page only displays session-local trajectory results. |
| Major issue | It is not a revision task and cannot load an eligible prior submission independently. |
| Minimal redesign | Learner ID; read-only candidate selection; read selected submission through the existing GET endpoint; show original prompt/text context and matching learner-facing practice target if present; revised-text input is primary; submit through the unchanged submission API with `revision_of_submission_id`; lock success against duplicate writes; show conservative trajectory/observation below. |
| Reused components | Student intro/context/action block, evidence/limitation notices, field error, loading/success/error states. |
| Acceptance | No eligible/eligible learner, empty input, one valid revision, exactly one revision record and applicable response observation, no refresh/locale duplicate, disclaimer present, forbidden claims absent, English desktop, Chinese mobile. |

No new API, service, schema, comparison, linkage, or response-observation logic
is introduced.

### 4.6 Learning Journey

| Contract item | Frozen decision |
|---|---|
| Purpose | Present the authoritative chronological record while separating activity, evidence status, source, and limitation. |
| Current primary action | Load Journey. |
| Major issue | Read-only state is hidden behind a load button; event metadata is compressed and may visually imply progress. |
| Minimal redesign | Load on valid learner ID through the existing read-only GET; chronology first; event label/time/source/evidence/limitation visually distinct; technical source IDs secondary; accurate empty and zero-priority states include a relevant CTA; descriptive boundary retained. |
| Reused components | Student intro/action block, timeline event, technical caption, empty/warning/limitation notices. |
| Acceptance | DEMO-001, S02 zero priority, empty learner, not found, order/source/evidence/limits, stable event count and dedup keys, zero refresh/locale/read writes, English desktop, Chinese mobile. |

The twelve event types, read-time derivation, deduplication, visibility,
version, source links, and FeedbackEngagementTrace decision are immutable.

Writing → Feedback → Practice → Revision → Learning Journey, in English
desktop and Simplified Chinese mobile. It must produce one submission, one
supported priority where the fixture permits, one target, one exercise
instance, one valid attempt, one evaluation, one revision, one applicable
conservative response observation, and one stable derived Journey, without
duplicate or render-triggered writes.

affected tests; Student regression; core pytest once; controlled and legacy
Student live verification once; 24 Student renders; 6 Research smokes; then
lifecycle, outage/recovery, cleanup, and exact `cmd /c "run.bat --verify"`.
