## 1. WU1 - Journey Cycle Model and Completion State

### 1.1 Objective

A learner-owned, read-only Journey cycle/view model that groups the existing
raw Journey events into coherent writing and Practice cycles with honest
student-facing states. No writes, no new raw events, no migration.

### 1.2 Implementation notes (targeted reconnaissance, WU1)

- Raw projection: `JourneyService.get_journey` (app/journey/service.py)
  reads eight learner-scoped record sets (now nine: exercises were added
  for attempt->target association), derives 12 raw event types, sorts,
  deduplicates, and classifies state. Raw contract unchanged.
- Persisted relationships used by the cycle model:
  - revision root: `essays.revision_of_submission_id` chain (plus
    `revision_group_id`/`revision_sequence` when present);
  - feedback: `feedback_records.essay_id` (INTEGER, unique per essay);
  - target provenance: `practice_targets.source_submission_id` +
    `target_json.source_priority_id` (`PRIO-{feedback_id}-{index}`);
  - attempt -> target: `exercise_attempts.exercise_id` ->
    `exercise_instances.practice_target_id`;
  - evaluation -> attempt: `practice_evaluations.attempt_id`.
- Priority provenance is validated read-only by parsing the stable
  reference (app/practice/mapping.py::parse_stable_priority_reference) and
  checking the persisted feedback record + index. Legacy (no reference)
  and unresolved references never gain fabricated provenance.
- The verified pipeline always creates analysis + feedback together; a
  submission without an analysis record maps to `insufficient_evidence`
  (matching the raw event vocabulary). The `submitted` base state is
  reserved in the vocabulary; the most informative state takes precedence.

### 1.3 Cycle view model (additive response)

`GET /api/v1/students/{id}/journey` keeps its existing fields and adds two
additive keys:

```text
cycles: JourneyCycle[]          # parallel read-only view
cycles_version: "journey-cycle-v0.9.7-c"
```

```text
JourneyCycle
├── cycle_id                    # "cycle-{anchor_essay_id}" (or
│                               #  "cycle-unlinked-practice")
├── learner_id
├── relationship_status         # linked | unlinked
├── root_submission             # JourneySubmissionView | None
├── revisions[]                 # JourneySubmissionView[]
├── feedback_stages[]           # JourneyFeedbackStage[]
├── practice_cycles[]           # JourneyPracticeCycle[]
├── current_state               # most advanced honest stage
├── chronology[]                # raw events of this cycle, raw order
├── available_actions[]         # empty in WU1; populated by WU2
└── limitations[]
```

```text
JourneyPracticeCycle
├── practice_target             # id/code/label/status/timestamps
├── source_submission_id
├── priority_provenance         # {status: valid|legacy|unresolved, ...}
├── exercise | None
├── attempt | None              # latest persisted attempt
├── evaluation | None
├── activity_state              # available | attempted |
│                               # evaluation_available |
│                               # evaluation_unavailable | completed |
│                               # unavailable (unsupported status)
├── evaluation_state            # not_applicable | unavailable | available
└── completion_state            # active | completed
```

### 1.4 Writing states

Per-submission `writing_state` (most informative, persisted activity only):

| State | Derivation |
|---|---|
| `revision_submitted` | essay has `revision_of_submission_id` |
| `insufficient_evidence` | root essay without an analysis record |
| `analyzed` | analysis exists, no feedback record |
| `feedback_without_priority` | feedback exists, zero priority items |
| `feedback_available` | feedback exists with priority items |
| `submitted` | base record state (reserved fallback) |

### 1.5 Practice activity states

| `activity_state` | Derivation (precedence) |
|---|---|
| `completed` | target status `completed` (evaluation may still be unavailable) |
| `evaluation_available` | attempt + persisted evaluation (active target) |
| `evaluation_unavailable` | attempt, no evaluation (active target) |
| `attempted` | attempt on a non-active, non-completed target |
| `available` | active target, no attempt |
| `unavailable` | unsupported status, no attempt (defensive) |

Attempts are authoritative saved work; evaluation unavailable never implies
failure, non-completion, or missing mastery. Completion is activity
completion only.

### 1.6 Grouping rules

- Cycle anchor = root submission resolved through persisted revision
  linkage; broken chains become controlled `unlinked` cycles (no
  cross-association, stable limitation).
- Independent essays => independent cycles (ordered by root submitted_at,
  then root essay_id).
- Practice attaches to the cycle whose submissions include the target's
  `source_submission_id`; unresolvable targets form the controlled
  `cycle-unlinked-practice` group.
- Cycle `current_state` = most advanced state among root writing state,
  revision states, and practice activity states (stable order documented
  in app/journey/cycles.py).
- `chronology` = the cycle's raw events in the existing raw ordering
  (submission anchor -> stage -> source id -> event type); deduplication
  keys remain unique.

## 2. WU2 - Safe Journey Navigation and Midpoint Integration

### 2.1 Objective

Allow the student to navigate explicitly from Journey cycles to existing
learner-owned records without writes or creation. Navigation carries stable
references only; destinations validate learner ownership; stale and
cross-learner references fail safely.

### 2.2 Action contract (view model)

`JourneyCycle.available_actions` (populated since WU2) contains descriptors
with stable references only:

```text
{"action": "open_revision", "submission_id": N}      # per submission with
                                                     # a persisted feedback
                                                     # record (root and
                                                     # revisions)
{"action": "open_practice", "practice_target_id": T} # per Practice target
                                                     # (active, completed,
                                                     # legacy, unlinked)
```

- No Feedback action: the Feedback page is session-scoped by design
  (v0.9.6-C1/v0.9.7-A); no reliable fresh-entry destination exists, so no
  action is fabricated.
- No action for submissions without a feedback record (the Revision page
  resolves candidates from persisted bundles; without feedback there is no
  reliable destination).
- Legacy and unlinked Practice records expose `open_practice` (the target
  preset resolves by id against the learner's persisted targets).

### 2.3 Navigation helpers (session state, references only)

- `_navigate_journey_revision(source_submission_id, lang)`: sets
  `revision_source_preset` + sidebar page. The Revision page re-reads the
  source and validates the reference against the learner's candidates.
- `_navigate_journey_practice(practice_target_id, lang)`: sets
  `practice_target_preset` (clears any lingering priority intent) + sidebar
  page. The Practice page validates the reference against the learner's
  persisted targets (id AND learner match) and renders the saved state.
- Navigation performs no database writes and never creates targets,
  exercises, attempts, evaluations, or revisions.

### 2.4 Destination fail-safe guards

- Revision page: when `revision_source_preset` was set but does not match a
  candidate of the current learner, an honest note
  (`student_revision_preset_invalid`) renders; no source is silently
  substituted without the note.
- Practice page: when `practice_target_preset` does not match a target of
  the current learner (id + `student_id`), an honest note
  (`student_practice_preset_invalid`) renders and the deterministic
  selection rule applies; no target is silently switched without the note.
- WU5 target-selection stability preserved: a valid Journey preset becomes
  the learner-scoped stable selection and survives reruns.

### 2.5 Locale delta

Two new keys (en/zh parity 574/574):
`student_revision_preset_invalid`, `student_practice_preset_invalid`.

### 2.6 WU2 acceptance

## 3. WU3 - Student Journey Functional UI Closure

### 3.1 Objective

Render the cycle view model as a clear, usable Student Journey page:
coherent writing cycles with original/revision distinction, feedback and
priority relationships, Practice activities with honest states, safe
actions, and empty/error/legacy handling.

### 3.2 Page structure

`render_learning_journey_page` (app/ui/features/student/journey.py) now
renders the grouped cycle view when `cycles` is present:

```text
Writing Cycle (cycle_id caption; cycle stage badge)
├── Original writing #id + writing stage + Open Revision (when a feedback
│   record exists)
├── Revised draft #id + "Revision of #source" + stage + Open Revision
├── Feedback and priority #feedback_id + priority count + category labels
└── Practice activity
    ├── target label + activity state badge
    ├── priority reference caption (valid) or legacy/unresolved note
    ├── attempt reference caption
    ├── completed wording (saved response/feedback remain available) or
    │   attempt-saved + evaluation-unavailable notice
    └── Open Practice (safe action)
```

- No-priority and insufficient-evidence stages render their honest
  descriptions; unlinked cycles render a warning + cycle limitation.
- The raw undifferentiated timeline is no longer the primary view when
  grouping data exists; a defensive timeline fallback remains for
  consumers without cycle data.
- Stable references appear only in secondary captions; internal
  identifiers are not the primary explanation.

### 3.3 Completion wording (frozen)

Allowed: "Practice activity completed" / "Your saved response and
formative feedback remain available" (reuses the WU5 completed keys;
without an evaluation, the attempt-saved + evaluation-unavailable notices
render). Disallowed wording (mastery/pass/improvement/CEFR/proficiency/
transfer/learning-gain claims) is excluded and asserted.

### 3.4 UI scope

Allowed: cycle grouping, headings, status badges via existing components,
action placement, existing component composition, new en/zh locale keys
(600/600 parity). Not allowed: new design system, broad restyling, global
typography, animation, dashboard redesign, comprehensive responsive work.
