## 1. Reconnaissance conclusions (evidence-backed)

- Evaluation schema: `practice_evaluations` (migration 12,
  `app/database/migrations.py:680`) stores `evaluation_json` with
  `attempt_id` and `practice_target_id`; evaluation is generated by
  `PracticeService.evaluate_attempt` (`app/practice/service.py:94`) and
  persisted best-effort by the attempt POST router
  (`app/api/routers/practice.py:135-148`); attempt row remains authoritative
  on evaluation failure (`attempt["evaluation"] = None`).
- Evaluation availability: no evaluation status field exists; availability
  is inferred from a persisted row for the attempt. `list_practice_evaluations`
  exists in the repository but has NO API route, so a refresh cannot restore
  the evaluation in the UI today (WU4 UI reads only the cached attempt
  payload; `app/ui/features/student/practice.py:116-127`).
- Target status: `PracticeTargetStatus` (`app/practice/schemas.py:13-19`)
  has ACTIVE/INACTIVE/PRACTICE_NOT_AVAILABLE/ARCHIVED; `COMPLETED` is a
  code-only additive enum value. Status is duplicated in the `status` TEXT
  column and inside `target_json` (`app/infrastructure/sqlite/repositories/
  practice.py:60-73`); reads load only `target_json`
  (`get_practice_target`, `list_practice_targets`).
- `practice_targets` has NO `updated_at` column and the `PracticeTarget`
  model has no update timestamp; `created_at` is the only persisted time.
  A completion timestamp therefore cannot update an existing column. Per
  the WU5 migration decision, no migration 14 is created; the completion
  timestamp is recorded in `target_json` via an optional model field.
- No repository update method exists for targets; one focused
  `update_practice_target_status` method is added (single transaction,
  conditional status update for concurrency safety).
- Journey reads targets/attempts/evaluations as records
  (`app/journey/service.py:285-335`); a new `completed` status flows through
  as `research_detail.status` and creates no new event type.
- WU3 create-or-reuse returns an existing target for the logical key
  regardless of status (`app/practice/target_creation.py:44-51`); a
  COMPLETED target is therefore reused, not duplicated.
- WU4 UI selection is active-only (`_selected_active_target`,
  `app/ui/features/student/practice.py:139-150`); the preset must be
  extended to any-status targets so a completed target remains reachable.
- `_ensure_current_exercise` (`app/ui/features/student/practice.py:75-96`)
  can create an exercise for a reused target; it must skip completed
  targets (no new exercise for a completed target).

## 2. Evaluation product semantics (frozen)

- The persisted evaluation is **automated formative feedback on the
  submitted Practice response**, computed by the existing rule-based
  algorithm. It is not proof of mastery, learning gain, transfer,
  proficiency, CEFR level, successful remediation, or readiness to advance.
- Persisted attempt = authoritative saved work. Evaluation = best-effort
  formative feedback. Evaluation failure never erases or invalidates an
  attempt.
- The evaluation algorithm and its persisted schema are UNCHANGED.

## 3. Evaluation availability states (frozen)

- **AVAILABLE**: a valid persisted evaluation row is associated with the
  selected attempt (attempt -> exercise -> target -> learner chain valid).
- **UNAVAILABLE**: the attempt exists but no valid evaluation row exists
  (best-effort failure, missing row, unsupported legacy data, or malformed
  row). The UI shows the attempt-saved confirmation plus an honest
  evaluation-unavailable notice; no fabricated evaluation and no false
  attempt failure.
- **MALFORMED**: a persisted row whose JSON cannot be parsed is treated as
  a controlled unavailable state (skipped server-side; never a page crash,
  never raw database details).
- No asynchronous PENDING evaluation state is introduced (persistence has
  no such state).

## 4. Evaluation read path (frozen)

One new learner-owned, read-only endpoint:
`GET /api/v1/students/{student_id}/practice-targets/{practice_target_id}/evaluations`
returns only evaluations whose full chain validates: target exists and
belongs to the learner; evaluation.attempt_id exists; the attempt belongs
to an exercise of the target; the attempt belongs to the learner. Any
violation or malformed row excludes the evaluation (controlled
unavailable). Cross-student access is rejected 403.

## 5. Completion eligibility (frozen)

> A learner-owned Practice target becomes eligible for completion after at
> least one valid persisted attempt exists for an exercise belonging to
> that target.

- A valid attempt: persisted `exercise_attempts` row with status
  `submitted`, belonging to the learner, on an exercise of the target.
- Evaluation availability is NOT a completion gate and NOT a mastery gate.
- No minimum score, correct answer, positive evaluation, or multiple
  attempts are required. This is activity completion, not learning-outcome
  certification.
- Completion eligibility is derived from persisted records only; session
  state is never proof.

## 6. Completion trigger and semantics (frozen)

- Trigger: one explicit student action `Finish This Practice Cycle`, shown
  ONLY after a persisted attempt exists on an ACTIVE target.
- Transition: `ACTIVE -> COMPLETED` (`PracticeTargetStatus.COMPLETED`,
  code-only; TEXT column stores `completed`).
- `COMPLETED` is terminal per priority reference: re-entry shows the saved
  result; WU3 create-or-reuse returns the same completed target; no new
  target, exercise, attempt, or evaluation is created.
- Repeated or concurrent completion is idempotent: one completed target,
  same target returned, no duplicate writes, no status conflict.
- Unsupported statuses (inactive/archived/practice_not_available) return a
  controlled error; no silent reactivation or overwrite.

## 7. Completion transaction (frozen)

New `SQLitePracticeRepository.update_practice_target_status(pid, status,
updated_at)`:

1. `BEGIN IMMEDIATE` (serializes with concurrent writers).
2. Conditional `UPDATE practice_targets SET status=?, target_json=?
   WHERE practice_target_id=? AND status=?` (old status `active`).
3. `target_json` updated in the same statement: `status` plus optional
   `updated_at` (ISO timestamp of the first completion).
4. Re-read and return the persisted target.
5. If the conditional update affects zero rows (already completed), re-read
   and return the completed target (idempotent success).
6. `updated_at` is set only on the first completion; repeats keep it.

New `PracticeTargetCompletionService.complete_target(student_id,
practice_target_id)` (in `app/practice/completion.py`) owns: target lookup,
learner ownership, attempt eligibility, status validation, transition, and
reconciliation. Business rules never live in the router.

## 9. Completion UI and re-entry (frozen)

- Active target with a saved attempt: saved-state block (attempt reference,
  response, evaluation or unavailable notice), a clear explanation that
  finishing closes this Practice activity, and `Finish This Practice Cycle`
  (pending guard via the shared submit-reliability helper, new
  `PRACTICE_COMPLETE` mode). Existing WU4 saved-state content is preserved.
- Completed target (any entry path): explicit completion heading, target
  label, saved attempt reference, evaluation (or unavailable notice),
  honest statement that the activity was completed and the response and
  feedback were saved, bounded next actions. No response form; no active
  finish button; no new exercise/target/attempt.
- Re-entry (rerun, refresh, locale switch, direct navigation, Feedback/
  Revision return, mobile sidebar): target status is reloaded from
  persistence every render.
- Failure before persistence: recoverable error, saved-attempt state
  preserved, finish action remains available, no false success. Uncertain
  response after commit: next rerun reconciles against the persisted target
  status (completed state renders).
- Selection: an explicit preset may resolve to any-status target
  (completed targets reachable); without a preset the deterministic
  oldest-active rule is unchanged.

## 10. Post-Practice next steps (frozen)

- `Return to Feedback` and `Open Learning Journey`: navigation only, no
  writes, no new Journey events.
- Another existing active target (when one exists): explicit user action
  opens it (target preset); no automatic selection, ranking, or sequencing.
- No automatic next-target creation and no automatic priority sequencing.
- No mastery/proficiency/CEFR/learning-gain/transfer/pass/improvement
  wording is introduced; `practice_boundary` wording stays.

## 11. Legacy targets (frozen)

A legacy target (no priority provenance) is completable when it belongs to
the learner and has a valid persisted attempt. No fabricated priority
provenance is created.

## 12. Migration decision (frozen)

**No migration 14.** Implementation uses the existing `status` TEXT column,
the existing `target_json`, an optional JSON-only `updated_at` model field,
and the existing attempt/evaluation tables. Migration 13 is untouched.
