## Findings

| Concern | Location | Finding | v0.2 action |
|---|---|---|---|
| Streamlit → database | `app/ui/streamlit_app.py` → `FeedbackPipeline` | Indirect: UI constructs a pipeline that constructs `Database`; no raw SQL in UI, but the process boundary is absent | replace with HTTP API client |
| Streamlit → Analyzer | same path | Indirect through in-process pipeline | move behind FastAPI application service |
| Streamlit → Diagnoser | same path | Indirect through in-process pipeline | move behind FastAPI application service |
| Streamlit → FeedbackService | `app/ui/streamlit_app.py:7,12-13,54` | Direct import, construction, and submit call | remove all business-service imports from UI |
| Streamlit → DeepSeek | through `FeedbackPipeline` | No direct Provider import, but UI process still owns Provider lifecycle | move Provider wiring to backend |
| SQLite connections/SQL | `app/database/repository.py` | Centralized in one concrete `Database`, but the business pipeline depends on that concrete class | split protocols from SQLite implementation |
| Migration mechanism | `Database.initialize()` | Schema creation plus ad hoc `_migrate_v0_1_to_v0_1_1`; no migration version/history | add numbered, idempotent runner |
| Global/UI state | `@st.cache_resource get_pipeline()` | Streamlit cache owns a stateful business object | cache only an API client |
| Mixed UI/business behavior | `app/ui/streamlit_app.py` | request validation and full in-process workflow are initiated in UI | serialize API request and render API response only |
| Route layer | absent | no unified backend contract | add FastAPI v1 routes and Pydantic API schemas |
| Repository coverage | absent as interfaces | one concrete class covers all aggregates | add named protocols and SQLite adapter |

## Protected path

`BasicAnalyzer` → `HeuristicDiagnoser` → history evidence → `PromptBuilder` → `ProviderRouter` → `FeedbackValidator` → persistence is working and must remain the single submission workflow. v0.2 will change dependency wiring and transport, not bypass these safeguards.

## Risk assessment

The refactor is feasible without deleting data or replacing the database. The highest risks are transaction boundaries during a multi-record submission, legacy-schema migration, and accidental UI backdoors. These are covered by explicit rollback, migration, static-boundary, and API integration tests.
