## 5. Unified reliability design

One shared internal mechanism for long-running essay submission:

```text
submit()  (public first-draft entry; also writing-page revisions)
submit_linked_revision()  (public linked-revision entry)
        ->  _submit_long_running()  (private shared transport)
                one POST, LONG_SUBMIT_TIMEOUTS, no retry
        ->  mode-specific reconciliation
```

### Shared client transport (app/ui/api_client.py)

- Private `_submit_long_running(submission)`: POST `/api/v1/submissions`,
  operation "submit", `profile=LONG_SUBMIT_TIMEOUTS` (2.0 / 180.0 / 180.0),
  no automatic retry (retry applies only to GET).
- Both public methods delegate to it. No new public method; frontend public
  method count stays 53.
- `DEFAULT_TIMEOUTS` (30 s write) remains for ordinary non-submission
  requests; GETs keep their existing profiles.

### Shared UI reliability (new internal module
`app/ui/features/student/submit_reliability.py`)

- Session-state pending/outcome keys per page (`writing` / `revision`);
  enter/release/consume pending; store and render outcomes.
- Outcome messages per mode: FIRST_DRAFT -> `student_writing_*` keys;
  LINKED_REVISION -> `student_revision_*` keys.
- No backend dependency; reliability state/logic only.

### First-draft reconciliation (writing page, mode-aware)

- Pre-submit baseline: one bounded GET of the existing
  `get_student_revision_candidates(learner_id)`; baseline = newest server
  `submitted_at` among rows of the same mode (first drafts:
  `revision_of_submission_id IS NULL`; writing-page revisions: rows with
  `revision_of_submission_id == source`).
- After a final timeout: re-fetch the same GET; exact candidates =
  same-mode rows with `submitted_at > baseline`; require exactly one;
  fetch the submission bundle and require student_id + exact essay text
  equality (text held in UI memory; never persisted); feedback present ->
  CONFIRMED_SUCCESS, else STILL_PROCESSING; zero/multiple/read failure/
  text or student mismatch -> UNCONFIRMED. Never POSTs, never recurses.
- No fuzzy or latest-only matching.

### Linked-revision freeze

v0.9.6-A reconciliation and messages are preserved; only the pending/outcome
mechanics are extracted to the shared module with behaviorally identical
session keys (`revision_submit_pending` / `revision_submit_outcome`).

## 6. User-facing messages (en + zh_CN)

- Pending: "Submitting and analyzing the first draft. This may take a few
  minutes."
- CONFIRMED_SUCCESS: "The first draft was submitted successfully."
- STILL_PROCESSING: "The request took longer than expected, but the first
  draft is still being processed. Check the submission history before
  submitting it again."
- UNCONFIRMED: "The request timed out before the result could be confirmed.
  The first draft may still have been received. Check the submission history
  before trying again."

Linked-revision messages unchanged. No "Please try again" and no Retry
button on any ambiguous submission timeout.
